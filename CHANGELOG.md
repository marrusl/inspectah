and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added
- **The refine Export dialog shows the export's warnings**: when an export comes with warnings, the dialog stays open after the download as "Downloaded, with warnings" and lists each one until you close it: a notice as information, and anything you asked for that is not in the export as a warning. Until now nothing displayed these, so an uploaded RPM the export could not verify and left out was dropped without a word in the UI. An export with nothing to report closes the dialog as before.
- **Refine lists the packages it does not carry and includes one with a click**: the Packages view has a "Not carried" group below the package list with every package the export leaves out as not needed, packages that own a unit enabled on the source host first and marked with their units. Include on a row carries the package: the export installs it, enables its units again and stops provisioning its `/var` directories, and the package moves to the package list, where you can exclude it again. Its own dependencies stay listed in the group, although dnf installs them with it. Until now these packages had no row in refine, so the only way to carry one was to know its name.
- **The refine Export dialog names not-carried unit owners before you download**: when the export leaves out packages that own an enabled unit, the dialog shows a collapsed information notice with their count, the names and units on expand, and a "Review not-carried packages" link to the Not carried group. The "Downloaded, with warnings" list no longer repeats that notice, so an export whose only warning was the notice now closes the dialog after the download.
- **Packages nothing in the image needs are listed as Not carried**: a package that was not user-installed on the source host, and that no package the image installs depends on, is no longer counted as part of the image. The scan tarball excludes it by default, and both the scan tarball and the refine export list it as `# Not carried: not user-installed on the source host, and nothing this image installs needs it (N)` in the Containerfile, one comment line per package, and as a `### Not carried (N)` table in the audit report with the package, its source repo and the units it had enabled. A package that owned an enabled unit is listed first and the Containerfile names the unit (`firewalld (firewalld.service was enabled)`). The test is the scan's leaf data: a dependency of a package you kept is still carried, because dnf installs it with that package. A kept package the image cannot install, one the Containerfile leaves as a manual step, does not count, so a dependency only it needs is not carried. Locked packages, packages installed at system install time, packages the baseline image ships, uploaded packages and repo-less packages keep their existing handling. When the scan has no leaf data, or the snapshot is a fleet aggregate, nothing is excluded and no list is shown. For a scan with a baseline and leaf data, an unchanged refine export installs the same packages as the scan tarball, except where refine applies its own rules: packages installed at system install time, repo-less packages, and a package only one of those needs, such as `dnf-plugins-core` when refine excludes the repo-less `epel-release` that pulls it in.
- **GPG keys in the snapshot record the `gpgkey=` path that named them**: a key a repo file names with dnf variables is recorded at its expanded path, and the new `gpgkey_references` field on the key holds the path as the repo file writes it, so anything that reads the repo file back can match the section to its key. The field is left out when the two paths are the same, and snapshots without it still load.
- **Unit state for every kind of unit**: the scan records and carries the enabled, disabled and masked state of sockets, paths, timers, targets and slices as it does for services, and of mount, automount and swap units that a package owns under `/usr/lib/systemd/system/`. A socket a package ships disabled and the administrator enabled, such as `cockpit.socket`, is now enabled in the image, and so is a vendor timer enabled against its preset; until now the scan read services only, and the state of every other unit was lost. A masked template is carried as a mask. A timer is a unit like the others: its state is its unit row, and a local timer's file is its Configuration Files row (a copy of a vendor timer is a Service Drop-ins row). `remote-cryptsetup.target`, which a stock RHEL 9 install leaves disabled against its preset, is left as the base image has it, so a stock host gets no `disable` nobody chose.
- **Advisories for the administrator's mount, automount and swap units**: a storage unit the administrator wrote (a unit file only in `/etc/systemd/system/`, a full copy of a vendor unit file, a vendor unit file no package owns, or a mask with no unit file) gets comment lines in the Containerfile's unit state section and never a `systemctl` line. They say the unit's state on the source host, whether its unit file is copied into the image, what its mount point means on a bootc host (under `/usr`, owned by bootc, under a link into `/var` such as `/srv`, or under `/opt`; an automount under a link into `/var` is told that its matching mount unit must be renamed too), a missing `nofail` option in the unit file, written only when the unit file's options were read and the unit has no drop-in that could set it, and the command to add by hand for an enabled or masked unit. That command is left out for a masked `tmp.mount`, for an enabled unit the advisory says to rename for `/var`, and for a masked unit whose unit file is copied in at its name, where `systemctl mask` would fail. `Where=` and `Options=` are read by logical line as systemd reads them, and `Options=` is split only at unescaped commas, so a line that continues a `What=` value is never taken for the mount point, and `Options=rw, nofail` does not count as `nofail`. The unit file stays a Configuration Files entry, decided on its own row. The mount source (`What=`) is not recorded. A fleet aggregate shows one advisory per unit, read from one host's copy of the unit; when more than one host recorded the unit, the advisory says so, since the copy staged may differ.
- **The export README says what a carried unit state means**: when the Containerfile carries at least one `enable`, `disable` or `mask` command for a unit collected from the host, the README's new Unit state section says that the states survive first boot with the base image's empty `/etc/machine-id`, that a later layer or installer script that removes that file or writes `uninitialized` to it makes first boot apply the presets, which can undo the rendered `enable` and `disable` lines (on RHEL 9 a `disable`, on RHEL 10 both) and keeps a `mask`, and that a `disable` removes only the administrator's links.
- **Refine shows each unit's kind and why the export leaves a command out**: in a single-host session, each row in Services shows its kind, and a row whose command the export will not write shows the reason, in the same words as the Containerfile's `# Omitted:` or `# FIXME:` line. An unlocked row inspectah flagged shows why. The administrator's mount, automount and swap units are listed after the unit rows with their advisory lines and a link to their unit file's Configuration Files row, and a configuration file or drop-in the export does not write shows why under its row. `/api/view` adds `kind`, `fragment`, `declined` and `unit_file_path` to unit rows, `kind` and `withheld` to drop-in rows, `withheld` to configuration file rows, and a `mount_findings` list. The fleet (aggregate) refine view does not yet show unit kinds, the reason a command is declined, withheld files or mount findings: they appear in the single-host view and in the Containerfile preview.
- **A converted cron timer has an include toggle in refine**: in a single-host session, each timer or `@reboot` service converted from cron has a toggle on its Scheduled Tasks row. Excluding it leaves its files and its `enable` out of the export, and including it brings them back. While the cron job it comes from is excluded, the row offers no toggle and says "Excluded with its cron job <path>; include the cron job to carry this unit." When two cron files generate one name, the row stays included, with its toggle, while either file's unit is still carried. A toggle that fails keeps its error on the row, announced to screen readers, until the next attempt or an Undo or Redo, even if you leave the section before the request settles; a request that fails after an Undo or Redo leaves no error. `/api/view` adds `generated_timers`, each with `name`, `include`, `locked` and, when its cron job is excluded, `cron_job_excluded`. A name is shown locked when any of its records is, so the row offers no toggle whose change the export would ignore.
- **Refine says why an unmanaged file under `/etc/systemd/system/` is not exported**: the Unmanaged Files row of an included file the export withholds there shows the reason under the row, in the same words as the Containerfile. Each unmanaged row in `/api/view` gains `withheld`, with the same fields as a config row's.
- **Hand-made unit links are reported with the line that recreates them**: a link under `/etc/systemd/system/` that a unit's `[Install]` section does not make, such as a `.wants` or `.requires` link made by hand, an `.upholds` link or an alias, no longer counts as the unit being enabled. The Containerfile's unit state section gives each one an advisory, comment lines only, saying why it is not carried, with the `RUN systemctl add-wants` or `add-requires` line that recreates a `.wants` or `.requires` link after the configuration `COPY`, and how to add an `.upholds` link or an alias by hand. A link to an instance of `systemd-cryptsetup@.service` or `systemd-fsck@.service`, which names a volume or device of the source host, is reported with no command. A link a package ships under `/usr/lib/systemd/system/` is never reported, and a link whose parent or own name is not a unit name gets a scan warning. A link the scan does not report for another reason also gets a scan warning naming the link and its unit and saying why, one warning per reason listing every such link: the unit is masked, so the link has no effect; it is a template under a plain parent with a unit file of its own name, which systemd starts as the instance named for the parent, and the warning names that instance (`bar@multi-user.service` for `multi-user.target.wants/bar@.service`); it is a template under any other parent, a link the scan does not read; it is an alias of a template, which the scan does not read either; it is changed by a file elsewhere on the search path; the link names the unit by an alias; there is no unit file of that name; or `systemctl list-unit-files` does not list the unit as one the scan reads. A warning names its first five links and counts the rest. A fleet aggregate holds the hand-made link findings and unreliable `[Install]` records of every host, a finding several hosts share once with the first host's reason by hostname order, and its Containerfile renders their advisories.
- **The source host's default target is carried**: when `/etc/systemd/system/default.target` links to a target, the unit state section sets it with `RUN systemctl set-default -- <target>`, before the other unit commands. It is left out with an `# Omitted:` line when the target's unit file is local or a replacement and that file is excluded, or when the target's package is not in the image. For an excluded replacement, the line names the file and says the image cannot set it as the default target. When the export carries another file at the target's name under `/etc`, the line names it and says the image cannot set the recorded file, and on a fleet aggregate whose hosts' files for the target differ, it says the export carries only one of them. A link that does not name a target with a unit file the scan reads gets a scan warning, and nothing is set. A fleet aggregate keeps the target most hosts set, included only when every host sets it.
- **Refine shows unit links, `Also=` members and the default target**: in a single-host session, the Services list shows each reported link, and each unit whose `[Install]` cannot be relied on, as a row with no toggle and the same advisory or `# Omitted:` lines as the Containerfile; when the export excludes one of the unit's `[Install]` files, the row lists the files that are not in the export. The default target is the first row, with its own toggle and the reason when the export leaves it out. It counts in the sidebar's decision count for the units view, and while the view holds it the bulk toggle's menu reads "Include all except the default target" and "Exclude all except the default target", and its announcement names the same exception. The note on the "Other drop-in overrides" group now says "These overrides have no unit-state decision row." instead of saying their units are at their preset state, which is not true of a unit whose `[Install]` the scan reports instead of carrying. A unit row lists the units its `Also=` reaches with what their links say on the source host, and a recorded `[Install]` drop-in listed under its unit's state row is marked `[Install]`; a drop-in with no state row above it is not marked. `/api/view` adds `manual_links` and `undetermined_installs`, `default_target` when the host sets one, and `also` and `install_drop_ins` on a unit row when they are not empty. The fleet (aggregate) view does not show these rows.
- **Enabled template instances are carried when their configuration is in the export, and omitted with the reason otherwise**: the scan used to drop every template instance without a word. It now records an instance enabled by a link under `/etc/systemd/system/` (`getty@tty2.service` in `getty.target.wants/`), an enabled instance with a unit file of its own, and a masked instance, with their state. A disabled instance that only its template provides leaves no link on the host, so the scan finds it from the preset rules (the template's `DefaultInstance=` under a bare `enable`, or each instance a rule lists) and from the `Also=` of enabled units. An instance at its preset, such as `getty@tty1.service`, has no state change and no line. Each instance is carried like any unit, a masked one as `systemctl mask`, and an enabled instance timer such as `worker@a.timer` has its schedule and the unit it starts read from its template. An instance's `enable` is carried only when every configuration file it reads under `/etc` is in the export as the host had it: the paths its unit file and every drop-in systemd applies to it (its own and its template's, the type-wide `service.d` and the dash-prefix ones such as `worker-.service.d`) name with `%i` or `%I`, read as systemd reads each setting (a quoted command argument such as `--config="/etc/app sites/%i.conf"` is one path, spaces and all, and an empty `EnvironmentFile=`, command or path list in a drop-in clears what came before it, as a new value of a one-path setting such as `WorkingDirectory=` replaces it, but only in a section that takes the setting and only when systemd accepts the new value, so an `EnvironmentFile=` under `[Unit]` or a relative `WorkingDirectory=-data` clears nothing), and for `wg-quick@`, `openvpn-client@` and `openvpn-server@` instances the file inspectah knows they read. The system manager's fixed directory specifiers are expanded (`%t` is `/run`, `%E` is `/etc`, `%S` is `/var/lib`), so `openvpn-server@` instances, whose shipped unit names `%t/openvpn-server/status-%i.log`, are carried like the client ones. An instance whose unit file names such a path in a form inspectah cannot read as systemd does, such as an unbalanced quote or a specifier it does not expand, or with a drop-in directory or drop-in the scan cannot read, is not carried: the Containerfile has an `# Omitted:` line for it naming the setting and the file and line it is on, or the file it cannot read, refine shows the same reason on its row, and the scan warns naming the same, never the setting's value, which can hold a credential. When such a file (or any file in a required directory) is excluded or cannot be staged, was not captured, is not in the export, or had a secret redacted (a WireGuard `PrivateKey`, for example), the Containerfile has an `# Omitted:` line naming the file and the reason, and refine shows the same reason on the row. A drop-in that clears or replaces such a path, or that hides a drop-in of its file name that names one, has to be in the export too, since the image reads the old path without it: when it is excluded, or sits under `/run/`, where no export carries it, the `enable` is omitted naming the drop-in. A file a package owns and the administrator did not change is not in the export, so such an instance is omitted too: add its `enable` by hand. A configuration path with a `..` component is always omitted, with a line saying inspectah cannot tell which file it reads, and so, on a fleet aggregate, is an instance whose configuration file differs between hosts. A carried instance that keeps data under `/var`, such as `dirsrv@example.service` in `/var/lib/dirsrv/slapd-example`, gets an `# Advisory:` line before the `systemctl` commands saying the image does not carry the data and the `enable` may start the unit on first boot. In refine, a carried instance's row notes each configuration file staged unredacted from a `--no-redaction` scan or holding a value the redaction pass flagged, and an instance of a template whose unit file names nothing it reads has a note saying inspectah does not know what it reads, followed, only when its `enable` is carried, by one saying it is carried on its unit file alone. The units list shows each instance's template, the configuration its `enable` needs and the paths that hold its data, and `/api/view` adds `instance_of`, `required_config` and `data_paths` to unit rows.

### Changed
- **Refine export warnings say how serious each one is**: the `x-export-warnings` header that `POST /api/tarball` returns is now a JSON array of `{"kind": ..., "text": ...}` objects, with `kind` either `failure` (something you asked for is not in the export, such as an uploaded RPM that could not be verified) or `notice`, instead of an array of plain strings. The list still stops at 20 entries plus an `...and N more` entry, which is a `failure` when any entry it stands for is one.
- **`inspectah scan` names packages it leaves out that owned an enabled unit**: after writing the tarball, the scan prints one line on stderr, such as this one from a stock RHEL 10.2 host: `Notice: 5 packages that own a unit enabled on the source host are not carried: audit, audit-rules, cronie and 2 more. See the Not carried table in audit-report.md and the # Not carried block in the Containerfile.`, with the same text the refine export's notice carries. It prints with `--quiet` too, never on stdout, and not with `--inspect-only`, which writes no tarball. The exit status is unchanged.
- **The refine export notes packages it leaves out that owned an enabled unit**: when the export does not carry packages that own a unit enabled on the source host, such as `firewalld` or `cronie`, `x-export-warnings` carries one `notice` naming how many there are and the first three, and pointing at the Not carried table in `audit-report.md` and the `# Not carried` block in the Containerfile. Include the packages in refine if the image needs them.
- **The scan tarball copies RPM-owned config files you modified**: a config file of an installed package that `rpm -Va` reports as changed in content is now included by default, the same as the package. The scan left these files out of `config/` and its Containerfile while a refine export with no decisions included them, so the two disagreed on files such as a changed `sshd_config`. They now agree, and the scan's audit report lists the files under Modified RPM-Owned Files. Exclude any you do not want in the image in refine.
- **A config file the scan could not read is reported instead of copied empty**: a config file over 256 KiB, unreadable, or not text was collected with empty content, and an export that included it wrote an empty file over the one in the image. This affected unowned files in `/etc` on both export paths, and modified RPM-owned files in a refine export. Such a file is now a `content_not_captured` advisory: neither the scan nor refine copies it, and the audit report, the HTML report and refine list it with the reason. If it also matches a modernization pattern, such as a file in `/etc/xinetd.d`, the reason gives both. Add it to the image by hand if you need it.
- **`inspectah aggregate` no longer counts a host that could not read a config file as agreeing with an empty copy**: hosts were grouped by file content, and a file a host could not read was collected with empty content, so it joined the group of a host whose copy really was empty. The merged entry then claimed every host, was included, and the aggregate tarball wrote an empty file over the one the other host could not read. A host that could not read the file is now its own `content_not_captured` entry with its reason and hosts, never the selected variant, and while any host's copy could not be read no copy of the file is included by default. A refine export of the aggregate no longer writes an empty `.content` file under `aggregate/variants/` for it either. The same holds when the hosts are refine exports: a config refine locks out of the image, such as `/etc/crypttab` or inspectah's own COPR repo file, keeps its `content_not_captured` advisory in the export instead of becoming an ordinary excluded entry with empty content.
- **Refine is documented as a workstation tool**: the docs now say to copy the scan tarball to your workstation and run `inspectah refine` there, since refine needs nothing from the scanned host. Running refine on the scanned host and forwarding the port is described as possible but not recommended: refine has no per-session authentication yet, so on a shared host other local users can reach its port. The forward uses `127.0.0.1` because `localhost` can resolve to `::1`, where refine does not listen. Windows is documented through WSL2 (untested). `inspectah refine` no longer prints the `If accessing remotely: ssh -L ...` line at startup.
- **A GPG key the base image already ships is not copied over it**: when a package in the base image owns a key file and `rpm -V` reports the file unmodified on the source host, the scan records the key excluded, with the reason `the base image ships it (<package>, unmodified on the source host)`, and raises no warning for it. The Containerfile names it in the GPG Keys section as `# Not copied: <path>: <reason>`, and the audit report lists it in a `### GPG Keys Not Copied (N)` table. This is how the stock Red Hat key is treated on RHEL, so a RHEL 9 host scanned against a RHEL 10 base image no longer copies its RHEL 9 key over the base image's. A key owned only by a package the base image does not have, such as EPEL's key owned by `epel-release`, is still copied, and so is a modified key, a key no package owns, and every key when the scan has no baseline image, the host is not package-based, or `rpm -Va` fails. Including a repo again in refine does not copy a key the scan left to the base image, and refine has no control to copy it. In a fleet aggregate a key is left to the base image only when every host that has it left it there.
- **The Added Packages count no longer includes packages that are not carried**: the `### Added Packages (N)` heading in the audit report counts the packages the image installs, so N drops by the size of the Not carried list. Those packages are named in the Not carried table instead.
- **A unit owned by a package that is not carried is omitted with that reason**: its `systemctl` lines are left out and the Containerfile records `# Omitted: firewalld.service (package 'firewalld' is not carried: not user-installed on the source host, and nothing this image installs needs it)`. A unit is omitted only when the existing presence rules already prove its owner absent, so a package with the same name at another architecture that the image does install keeps its unit.
- **`/var` directories of packages a kept package pulls in are no longer provisioned**: the `/var` evidence now counts a package that an installed package depends on as carried, so the Containerfile no longer creates a directory for it and the tmpfiles fragment no longer says its creator is missing.
- **Sysctl files are carried as the host had them**: each file under `/etc/sysctl.d/`, and a modified `/etc/sysctl.conf`, is now an ordinary Configuration Files entry, copied into the image unchanged and under its own name, so the image applies the same settings in the same order as the host did. inspectah no longer picks keys out of the files and rewrites them into a file of its own, which put every setting at one position and left the source files out. Files in `/usr/lib/sysctl.d/` and `/run/sysctl.d/` are not copied. An `/etc` sysctl file whose path the export refuses, such as a name holding a line break, is not copied either, and the reports list it as not carried with the export's reason rather than saying it replaces a vendor file on the target.
- **Runtime sysctl drift is reported, not carried**: a key whose running value differs from the value the files request is listed in the audit report, the HTML report and refine, with the file and line that set it. A tuned profile, a hand-run `sysctl -w` or another service can cause this, and the image gets the files, not the running values.
- **System Tuning is a section in refine again**: it holds the tuned profile row and a read-only sysctl panel, in single-host and fleet sessions. The panel shows each key's effective value, running value and source line, runtime drift, vendor files an `/etc` file replaces or disables, files that are not carried and why, and lines reported as written, such as globs; the panel's Files table links each file to its Configuration Files row where it has one. On a fleet aggregate the panel, the audit report and the HTML report say in one line that the sysctl explanation is per host, and sysctl files merge like any config file, with a variant per differing content.
- **The sysctl explanation follows systemd's precedence**: files are resolved the way systemd-sysctl applies them. A file in `/etc/sysctl.d/` replaces a file of the same name in `/run/sysctl.d/`, `/usr/local/lib/sysctl.d/` or `/usr/lib/sysctl.d/`, a later line overrides an earlier one, a `-<key>` line excludes a key set earlier, and `net/ipv4/ip_forward` and `net.ipv4.ip_forward` are one key, as are spellings with a leading, trailing or repeated separator, so `-/vm/swappiness` excludes `vm.swappiness` as systemd reads it.
- **The audit report's sysctl table shows file and runtime values**: `#### Sysctl Overrides` is now `#### Sysctl`, with a `Key | File value | Runtime value | Source` table covering every key the files set, where the runtime value reads `same` when it matches and `not exposed` when the kernel does not list the key.
- **Sysctl values are left unstated when inspectah does not know every input**: a sysctl file inspectah could not read makes the explanation unavailable and the report gives the reason. A sysctl file or running value that redaction changed, or a link to a file outside `/etc/` and the sysctl directories, makes the reports state no values or drift for the host and name the file or key, rather than show values that could be wrong. The files are still carried as Configuration Files. A secret in a sysctl file or running value is listed in `secrets-review.md` once: under the file's path, or under `/proc/sys` for a running value. An `/etc` sysctl file that is also a Configuration Files entry is listed once for each secret, not once per copy.
- **An RPM-owned config symlink re-pointed to `/dev/null` is carried as an empty file**: `rpm -Va` reports such a link only through its link flag, so the scan dropped it and the image lost the mask. It is now carried as an empty file of the same name, which has the same effect as the link for files read by name, such as sysctl.d files. This covers a masked `/etc/sysctl.d/99-sysctl.conf`, and any other `/etc` package link masked the same way. A package link re-pointed to any other file is still not carried.
- **Snapshots from earlier releases must be re-scanned**: the snapshot schema is now 28, and `refine` and `aggregate` load only schema 28. Re-scan each host; aggregates re-aggregate from the re-scanned hosts.
- **Refine shows a full unit shadow on its drop-in row only**: when `/etc/systemd/system/` holds a replacement for a vendor unit file and the unit is otherwise at its preset, refine no longer adds a state row for the unit. The shadow, its badge and its explanation are on the drop-in row, which has the include toggle for the file.
- **The reports call the unit section "Unit State Changes"**: the HTML and audit reports headed it "Service State Changes". The HTML report's section anchor is `#units` instead of `#services`, and its filter box reads "Filter Units".
- **The aggregate detail pane shows Kind "Unit" for unit rows**: it showed "Service".
- **Unit names are checked against systemd's naming rules**: a unit name in a snapshot's unit state changes or unit inventory, or in a refine operation on a unit, must be 1 to 255 bytes of ASCII letters, digits and `:_.\@-`, and end in a type suffix inspectah knows (service, socket, path, timer, target, slice, mount, automount or swap). A snapshot that holds another name does not load, an operation that names one is refused, and the error names the rule the name broke. The scan records a warning for such a name and leaves it out of the unit inventory and state changes. `.device` and `.scope` units, which the scan does not record, get no warning.
- **Unit commands run after the files they name, in one section**: the Containerfile writes `enable`, `disable` and `mask` under `# === Systemd Unit State ===`, which replaces `# === Service Enablement ===`, after the configuration and drop-in `COPY` lines instead of before them. Each verb is one `RUN systemctl <verb> --` with every unit on its own line, ordered by kind and then by name. A unit name is single-quoted only when the shell would otherwise change it, as it would the `\` of an escaped name such as `backup\x2djob.timer`; `httpd.service` stays bare. The timers and `@reboot` services the Scheduled Tasks section converts from cron, and `flatpak-provision.service`, are written the same way in their own sections, each after its own `COPY`, and a cron timer or `@reboot` service only under a name that passes the unit name check: an escaped name such as `backup\x2djob.timer` is enabled, and a name with a control character gets a `# FIXME:`. Every `systemctl` line in the Containerfile comes from one plan. The drop-ins count reads `# N unit drop-in(s)`, since drop-ins of every kind are carried, and a degraded units inspection is noted as `# FIXME: units data may be incomplete`.
- **A unit command the export cannot reproduce is left out with the reason**: the unit state section writes `# Omitted: <unit> (<reason>)` instead of a command that would fail or do something other than what the source host had: an enable or disable of a local unit whose unit file is excluded, of a shadowed unit whose replacement file is excluded, of a vendor unit with another unit file copied in at its name, or of a package-owned mount, automount or swap unit with the administrator's file copied in at its name; and a `mask` where a unit file is copied in at the same name, since `systemctl mask` fails on a regular file there. Refine shows the same reason on the row.
- **Units the image needs are never switched off**: a `disable` or `mask` of `bootc-*`, `ostree-*` or `systemd-remount-fs.service`, and a `mask` of `tmp.mount`, are not carried. The Containerfile writes a `# FIXME:` saying the image needs the unit, or for `tmp.mount` that without it `/tmp` is read-only on a bootc host, and refine shows the same reason on the row. An `enable` of any of them is carried.
- **Package updaters that run in place are excluded by default**: `dnf-automatic*.timer` and `packagekit-offline-update.service` are recorded with their state and excluded by default, with a reason saying an image-based host is updated by a new image, and the Containerfile names each in an `# Omitted:` line. Include one in refine to carry it anyway. The default also covers a `disable` or `mask` of one, and a `dnf-automatic` timer whose file is in `/etc/systemd/system/`, local or a copy of the vendor timer. `packagekit-offline-update.service` is no longer locked as incompatible with image mode, so it can be included.
- **A shadowed unit's command depends on its replacement file, not its package**: a service, socket, path, timer, target or slice whose file the administrator replaced in `/etc/systemd/system/` gets its `enable` or `disable` when that file is copied, whether or not its package is in the image, since the image loads the `/etc` file. The rule for units the image needs still applies, and a fleet aggregate leaves the command out when the hosts hold different versions of the file. The administrator's full copy of a mount, automount or swap unit gets an advisory and never a command. A mask follows its package like an `enable` does: a mask of a package's unit is left out with an `# Omitted:` line when the package is not in the image, and carried when the package is included or the base image ships it, or when no package owns the unit. It is also left out, with its own reason, for a unit the image needs, `tmp.mount` included, and where a unit file is copied in at the same name; those reasons come before the package's.
- **An enabled local unit is carried with its unit file**: a service, socket, path, timer, target or slice whose file is only in `/etc/systemd/system/` and that is enabled now gets an `enable` whatever the presets say, when its unit file is copied, since the image has the unit only if the export carries it. A fleet aggregate leaves the `enable` out when the hosts hold different versions of the file. The administrator's local mount, automount or swap unit gets an advisory and never a command. A disabled local unit no longer gets a `disable`, since a copied unit file is not enabled until something enables it. A unit file a package owns in `/etc/systemd/system/` counts as local.
- **Units the scan cannot place get a warning instead of a command**: a unit whose file, or an `[Install]` drop-in of it, sits in another directory on systemd's search path, where it changes which file loads or what `enable` does (`/usr/local/lib/systemd/system/`, `/run/systemd/system/`, `/etc/systemd/system.control/` and the rest), an alias, and a link to a unit file elsewhere each get a warning naming the unit and the path, and no state change, whatever the unit's state. A link that ends at `/dev/null` or at a zero-length file is a mask, not an alias.
- **Manual follow-up lines give the advice as its own sentence**: the Containerfile's `# TODO:` line for a package installed locally, with no repository source, or with no recorded repository source joined the reason and the advice with a dash. It now ends the reason with a full stop, as in `# TODO: 'tool.x86_64' was installed locally (state: local_install). Provide a .rpm or custom repo.` A script that matches the old line needs the new text.
- **The scan progress line for units reads "Units"**: it read "Services", and its count now covers state changes of every unit kind. The not-carried notice and the Not carried list name packages that own an enabled unit of any kind.
- **A unit inspectah generates never replaces one collected from the host**: when a timer or `@reboot` service converted from cron, the service paired with a converted timer, or `flatpak-provision.service` has the name of a unit the scan collected, no generated file of that unit is written, the paired service of a generated timer included, and the generated unit is not enabled. A collected unit here is one whose state change is included, one with a Configuration Files or Service Drop-ins row included at that path, or one the scan lists in its unit inventory with no state change, such as a package's unit at its preset. The Containerfile says so in its section with a `# FIXME:` that names the unit that has the name: for a unit with a row, `# FIXME: <unit> (inspectah generates this unit, and a unit collected from the host, <collected unit>, has the name of one of its files, so the generated files are not written and the unit is not enabled here; to carry the generated unit, exclude the collected unit and its file)`, and for a unit with no row to exclude, a FIXME that says the host already has a unit of that name and that the job is carried by writing its timer and its service by hand under other names. The configuration FIXME names the withheld files. The collected unit keeps its own state: a vendor timer of that name is enabled from the unit state section, and a local timer the host had disabled stays disabled. On a rescan of a host built from an inspectah image, the collected `flatpak-provision.service` is carried and the generated one is left out until you exclude both the collected unit and its file in refine. Two cron entries of one name still write the last one.
- **The flatpak provisioning service is enabled after its own `COPY`**: the container workloads section copies `flatpak-provision.service` and then enables it as `RUN systemctl enable --` with the unit on its own line, only when the export writes the file. Generated cron timers and `@reboot` services are enabled the same way in one instruction in the Scheduled Tasks section, after a comment naming the `@reboot` services.
- **Refine shows a declined generated unit on its row**: in a single-host session, a converted cron timer or the flatpak applications show why the export does not enable the generated unit, in the same words and with the same marker as the Containerfile: a FIXME for a name collision, and an Omitted line when a generated file is not in the export for another reason. `/api/view` adds a `declined_generated` list, keyed by the generated row's name, which the row carries as `generated_timer`.
- **A scheduled timer row links to its unit row**: in refine, an existing timer's Scheduled Tasks row names its unit (`<name>.timer`) and links to that unit's row when the timer has one, found by its exact name, a backslash included (`backup\x2djob.timer`); the row itself has no include toggle.
- **The Containerfile says which local timers it carries**: the Scheduled Tasks comment `# Existing local timers (N): ...`, which listed every local timer whether or not its file was in the export, is now `# Local timers carried with their configuration or drop-in row (N): ...` for the timers whose file the export writes and `# Local timers not carried (M): <name> (its unit file is not in the export)` for the rest, each line left out when empty.
- **A local or shadowed timer's file has one control**: a timer whose file is in `/etc/systemd/system/` is copied by its Configuration Files row, or its Service Drop-ins row when it is a copy of a vendor timer, and by nothing else. Excluding that row leaves the file out of the export, and the timer's `enable` or `disable` is left out with the reason.
- **Scheduled Tasks rows are identified by their kind and source**: in `/api/snapshot/sections`, every scheduled row's id is now `<kind>:<source>`: `cron:<path>`, `timer:<path>` (`timer:<name>` when the snapshot records no path), `timer-instance:<pair>`, `at:<file>` and `generated:<index>:<name>`, where `<index>` is the row's place among the generated units. An instance timer is described from its template's file, which it records as its path, so its row is `timer-instance:` followed by the JSON array `[path, name]` (`timer-instance:["etc/systemd/system/worker@.timer","worker@a"]`), and the template's row and each instance's row keep their own ids. Rows that share a name, such as a shadowed timer's `/etc` and vendor files, or a collected timer and a converted cron timer of one name, used to share an id, so a search or a link could land on the wrong row. Join a generated row to `declined_generated` and `generated_timers` through its `generated_timer` field, not by reading the id.
- **Enablement is read from a unit's links, not from systemctl's word**: `systemctl list-unit-files` says `enabled` when it finds any link to a unit, whoever made it. The scan now reads the links each unit's effective `[Install]` section names, from its unit file and drop-ins, against the links under `/etc/systemd/system/` and the links packages ship under `/usr/lib/systemd/system/`. A unit is enabled when every link its section names is present and at least one is under `/etc`, and disabled when none is under `/etc`, so links a package ships complete an install and never start one. An alias counts for the unit its whole chain of links ends at, and a link to a file outside the two unit directories is no alias, whatever the file's name. A chain the scan cannot follow, because a link on the way cannot be read, degrades the scan, and no unit gets a state from the incomplete links. A unit enabled only by a hand-made link is reported (see Added) and not enabled, and a unit with some of its links and not others, or whose `[Install]` names no link, gets no state change. A link of a unit with some of its links that its section does not name is reported as hand-made, and only the links the section names are listed as the ones present. The unit inventory records the state read from the links, and a unit with no install state of its own has no entry; when the preset files cannot be read, the degraded inventory still records systemctl's word. A preset line that lists instances (`enable getty@.service tty2 tty3`) applies only to those instances. A preset line with a verb the scan does not read stops the lookup for the units it matches, and the scan warns, naming the line, its file and the units it decided. A listing under `/etc/systemd/system/` or the vendor unit directory that fails part way degrades the scan naming the directory and gives the units it could hide no state, where it used to drop the entries it could not read and could read an enabled unit as disabled; a timer's drop-in directory that fails so leaves the timer's trigger unresolved. A preset directory whose listing fails part way, or a preset file that cannot be read, degrades the scan naming it, and no unit gets a state change from the presets read, since a missing rule can turn a change either way; the inventory records systemctl's word, as when no preset can be read. A listing of `/etc/systemd/system/` or the vendor unit directory that fails while timers are described degrades the scheduled tasks naming the directory, and when it is the `/etc` one, no vendor timer's trigger is taken as the unit the timer starts.
- **An `[Install]` section the scan cannot rely on is advised, not carried**: the section is read as `systemctl enable` reads it: an empty `WantedBy=`, `RequiredBy=` or `Alias=` in a drop-in clears the values before it, an empty `Also=` does not, and the type-wide (`service.d`) and dash-prefix (`a-.service.d`) drop-in directories are not read for it. A unit whose section holds an `UpheldBy=`, a specifier the scan does not expand (any but `%i`, `%p` and `%N`: `systemctl enable` does not expand `%I`), or a name it does not admit, gets no `enable`, and each of its links is reported with that reason. When it also has an `[Install]` file under `/etc/systemd/system/` or assigns `Also=`, it gets one advisory saying the image's links can differ from the source host's, and no `disable` either. With no link under `/etc` and neither of those, it is disabled. A unit whose unit file or `[Install]` drop-in cannot be read as text is treated the same way, as if it assigned `Also=`: it gets the advisory and neither command, whatever `systemctl list-unit-files` says, and the scan warns, naming the file. A mount, automount or swap unit under `/etc/systemd/system/` with such a section gets this advisory and no mount advisory, so nothing says it is not enabled when its state is not known. Of two `[Install]` drop-ins of one name, one in an instance's own directory and one in its template's, the instance's is read, as systemd does. A drop-in in a directory systemd ranks above `/etc/systemd/system/`, such as one `systemctl set-property` writes under `/etc/systemd/system.control/`, hides an `/etc` drop-in of its file name, so an `[Install]` section in the hidden file is no longer read. An image without the hiding file reads the hidden one, so when the unit's `enable` or `disable` depends on it, the command is carried only when the export copies the hiding file too: never for one under `/run/`, and for one under `/etc/systemd/system.control/` only while its configuration file is included. Otherwise the command is omitted, naming the hiding file.
- **A unit at its preset whose `/etc` files change `[Install]` is carried or advised**: the package install in the image links a preset-enabled unit from the package's `[Install]` before the configuration `COPY`, so the links a full shadow or an `/etc` drop-in gave the unit on the source host were lost with nothing said. When the `/etc` files only add links (a `WantedBy=`, `RequiredBy=` or `Alias=` the package's unit does not name), the unit now gets an `enable` after the `COPY`, which adds them, and its refine row says why. When the files drop or replace a link, each difference gets an advisory and no command: a link only the source host has gets the `add-wants` or `add-requires` line, a link only the package install makes gets a `RUN test -L <path> && rm -- <path>` line that removes it only if it is a link, or, when the export copies a file to that path, a line saying the file replaces the link, and a difference in `Also=` gets an advisory with no command. When the package's `[Install]` is one the scan cannot rely on, such as one with an `UpheldBy=`, the unit gets the advisory an `[Install]` section the scan cannot rely on gets, naming its `/etc` files, whether or not it has a link, and no command, and each of its links is reported with that reason. When the export excludes one of those `/etc` files, the unit's advisories become one `# Omitted:` line naming the excluded files. A shadow or drop-in that leaves `[Install]` alone changes nothing. A `static` unit with a file or drop-in directory of its own name under `/etc/systemd/system/` is now read too.
- **A command whose `Also=` members differ on the source host is an advisory**: `systemctl enable` and `disable` also act on every unit an `[Install]` section names in `Also=`, and on the units those name. The scan records those members and what the links say about each, and an `enable` or `disable` of such a unit is carried only when every member's links on the source host match what the command does, each member with a row of its own is carried with the same verb, and neither the unit nor a member has an `[Install]` file under `/etc/systemd/system/`, copied or excluded. Otherwise the Containerfile holds an advisory that names every member keeping the command from being carried and, where it can, the lines to add by hand. Those lines never disable a unit the image needs, such as `bootc-fetch-apply-updates.timer`: the advisory names it instead. When a member's links neither command reproduces, or a line is left out that way, the advisory says the lines do not reproduce the source host. A packaged unit at its `enable` preset whose `Also=` member is not enabled on the source host is now an enabled state change with a note, so it gets that advisory too. In a fleet aggregate, a command for a unit with `Also=` members is always an advisory, with the command to add after checking the unit and its members in the image. A fleet aggregate merges a unit's `Also=` members and `[Install]` drop-ins from every host that recorded the unit, so a command whose `[Install]` drop-in only some hosts have is left out, with an `# Omitted:` line, until that drop-in is included.
- **Refine's Services section is now Systemd units, grouped by kind**: in a single-host session, the sidebar entry and the section heading read "Systemd units", and the heading no longer carries a count of shadow overrides. Rows sit in collapsible groups: Default target, Services, Sockets, Timers, Paths, Other units and Reported, not carried, sorted by unit name, and a row stays in place when you include or exclude it. A group's count badge is the number of unit rows or reported rows it shows, with drop-ins left out; the Default target group, and a kind group that shows only orphan drop-ins, have no count. A kind group's header flags how many of its rows need follow-up. A Show bar with All, Needs follow-up, Carried and Excluded, each with its count, filters the rows, announces how many are shown, and keeps a row you just toggled in view. The default target has its own group with a line saying that, included, the image boots to it too. Each row shows its state and `preset: <state>`, an outcome label (FIXME, Advisory or Omitted, the Containerfile's own word) when inspectah declines to carry its command, which a row you excluded does not show, and one reason instead of two; a unit with no package shows `(local)`, `(shadowed)` or `(absent)`, and an instance names its template on the first line. The "Non-Default State" badge is gone from this section. An `Also=` member and a path a unit needs link to their own rows when they have one, and the reported rows sit together per unit: a link row names its relation ("wanted by", "upheld by") and carries a cause label, an undetermined-install row gives its reason in words and a cause label, and a mount unit's row shows its kind, a link to its file and its advisory lines, with no cause label. A row that cannot be toggled, or a drop-in under an excluded unit, is shown dimmed, with its status badge and keyboard focus outline at full strength, and after "Show all" or "Clear filter" the keyboard focus moves to the filter's "All" button or the search box instead of being lost. The drop-in badge reads "Unit excluded", orphan drop-ins sit at the end of their kind's group, and the badge on a configuration file a drop-in controls reads "Controlled in Systemd units", and the explanation beside it says the Systemd units row for that path carries the file into the image and that you decide it there. Links from Scheduled Tasks, `Also=`, "Go to owner" and global search land on the row even under a filter or in a collapsed group, global search finds every row including a unit by the reason it was omitted, and `j`, `k`, the arrow keys, `g` and `G` move between rows across groups; these keys, with Space and `x`, are ignored while Ctrl, Cmd or Alt is held. On a narrow window the rows wrap, a long unit name breaks and its badges move under it, and the outcome bar wraps onto more lines, with no sideways scrolling. The fleet view is unchanged and still says "Services".

### Removed
- **`99-inspectah-migrated.conf` is no longer written**: the scan tarball and the refine export no longer contain a `sysctl/` directory, and the Containerfile no longer has a `COPY sysctl/` line. The host's own sysctl files carry the settings instead.
- **The per-key sysctl toggle in refine is gone**: sysctl keys are no longer decisions. Each `/etc` sysctl file is included or excluded by its Configuration Files row, and the "Merged into sysctl settings" badge no longer appears.
- **The refine export no longer writes `systemctl enable` or `disable` for a unit whose only change is a full shadow**: for an enabled or disabled unit with a full shadow in `/etc/systemd/system/` and no state change of its own, refine added a state row the scan did not find, and the export wrote that row's `systemctl` line. Refine no longer adds the row, so the export no longer writes the line. The shadow file is still copied. The scan export never wrote this line.
- **The scheduled timer toggle in refine is gone**: a scheduled timer's row had an include toggle that was accepted and applied nothing. The row is now a description, and the timer's state and file are decided on their own rows. The fleet (aggregate) view no longer lists scheduled timers with a toggle, and the Scheduled Tasks bulk toggle no longer sends timer operations. A refine request naming the operation is refused, and a saved refine session that holds one no longer loads: start over with `--fresh`.
- **The kernel and boot section no longer enables `tuned.service`**: it wrote `RUN systemctl enable tuned.service` whenever tuned activation was included, after the unit state section, which undid a carried `disable`, made a carried `mask` fail the build, and failed the build with the `tuned` package excluded. The section still writes the active profile. The unit's own row decides: a host that enabled `tuned.service` against its preset gets the enable from the unit state section, omitted when the `tuned` package is excluded, and a host that disabled or masked it keeps that.

### Fixed
- **`inspectah aggregate` accepts hosts that have no hostname**: two or more scans of hosts with no name, such as DHCP-named cloud instances, were refused as `duplicate hostname: <unknown>`. Each unnamed scan now aggregates as its own host, listed as `<unnamed N, scanned <time>>`, and only the same snapshot given twice is refused.
- **A scan names a host whose `/etc/hostname` is empty**: on a DHCP-named host, such as a cloud instance or a provisioned VM, the snapshot carried no hostname, so the refine header was blank, the refine export was named `inspectah-inspectah-refined.tar.gz` and the report named the host `unknown`. The scan now falls back to the host's transient name and records which source supplied it.
- **An SELinux port label excluded in refine stays out of the export**: the Containerfile wrote `RUN semanage port -a` for every port label the scan found, whatever its disposition, and installed `policycoreutils-python-utils` for it. An excluded port label now renders neither, and is not counted in the block's port label comment.
- **The refine download installs package groups as the preview shows**: a downloaded Containerfile named no `dnf group install` and installed a renderable group's members one by one, while the preview showed the group install. The download now matches the preview.
- **The source host's machine-id is never copied into the image**: rendered unit states survive first boot because the image keeps the base image's empty `/etc/machine-id`. A scan never records the file, but an imported snapshot could offer it as a configuration file, a drop-in, a repo file or an unmanaged file, and the export would have copied it. Every such offer, however its path is spelled, is now left out, and the Containerfile names it in a `# FIXME:` under Configuration Files. In refine, each row that offered it shows why under the row.
- **The image no longer carries the source host's Insights and subscription identity**: the scan copied the files insights-client and subscription-manager write at registration (`/etc/insights-client/machine-id`, the client's dot-named state files such as `.registered` and `.lastupload`, `/etc/rhsm/facts/insights-client.facts` and the product certificates in `/etc/pki/product/`), so every machine deployed from the image claimed the source host's registration. Those files are now left out of the scan. Configuration the admin writes in the same directories, such as Insights `tags.yaml` and redaction rules or custom facts in `/etc/rhsm/facts/`, is still carried.
- **A disabled local timer is no longer enabled in the image**: the Scheduled Tasks section enabled every timer whose file was in `/etc/systemd/system/`, whatever its state on the host, and copied its files even when their Configuration Files rows were excluded. A local timer is now enabled only when the host had it enabled, from the unit state section, and its file is copied only by its own row.
- **A vendor timer enabled against its preset is carried**: a timer a package ships, enabled on the host against a `disable` preset, gets its `enable`, including when a cron entry converts to a timer of the same name, whose generated files are then left out.
- **Excluding a generated cron timer in refine leaves it out of the export**: `SetInclude` on a converted cron timer's row was accepted and applied nothing, so its files and its `enable` stayed in the export. Excluding the row now removes the generated timer, its service, their `COPY` and the `enable`, and including it restores them. Excluding a cron job's row removes every unit generated from it the same way, and while a cron job is excluded, including one of its generated units is refused with both rows named, so the two rows cannot disagree. A cron job that generates no unit, and an at job, which the export never carries, refuse the operation by name instead of accepting it. The Scheduled Tasks bulk toggle no longer sends those refused operations. Refine's decisions list each generated timer with its include state (`generated_timers`).
- **A timer whose trigger the export does not carry is not enabled**: with one writer per file, you can exclude a local timer's service in refine and keep the timer, and systemd does not start a timer whose unit is missing. The scheduled inspector now records each timer's trigger, its `Unit=` with `%i`, `%p` and `%N` expanded, or the same-named `.service` when it sets none, and the drop-ins under `/etc/systemd/system/` that the trigger depends on: the one that sets the first accepted `Unit=`, and one before it that hides a drop-in of its name. As systemd reads it, the first accepted `Unit=` in the timer's file and drop-ins is the one that counts and a later one does not override it. An empty `Unit=`, one naming the timer itself, and one holding `%I` or a directory specifier such as `%t` ("Invalid slot") are ignored as if absent, so a timer whose only `Unit=` is one of these starts its same-named service, and a drop-in holding only such lines does not affect whether the timer is carried, unless it hides another applicable drop-in. A `Unit=` naming another timer is not resolved, and the timer's `enable` is not carried. A hidden drop-in such as `.override.conf` is skipped, as systemd skips it. The timer's `enable` is left out with an `# Omitted:` line when one of those drop-ins is not in the export, when `Unit=` cannot be resolved to a unit name, or when the trigger is a local unit whose file is not in the export and no staged generated unit or package in the image provides it. A `disable` or `mask` of a timer is unchanged. A timer's Scheduled Tasks description gains `trigger` and `trigger_drop_ins`.
- **An unmanaged file is never written under `/etc/systemd/system/`**: an imported snapshot and tarball could offer an unmanaged file or link there, which the export copied after the unit state section, replacing a unit file the plan had already decided. Such a file, at any depth below the directory and however its path is spelled, is now not bundled by a scan, not extracted by a refine export, and gets no `COPY` or `ln`; the Containerfile names it in a `# FIXME:` that says a unit file belongs under Configuration Files, and refine's decisions list it as withheld (`unmanaged_withheld`). The rest of the export is unchanged.
- **Excluding a repo in refine drops its `.repo` file and GPG key**: excluding `epel` removed its packages, but the export still copied `/etc/yum.repos.d/epel.repo`, with `[epel]` enabled, and EPEL's GPG key. The file also holds `[epel-debuginfo]` and `[epel-source]`, which the host keeps at `enabled=0`, and refine counted those sections as still in use. A section the host disabled no longer keeps a repo file or a key: a `.repo` file is copied while at least one of its enabled sections is included, and a key while an included, enabled section names it. Excluding `epel` now leaves both out of the config tree and out of the Custom Repositories and GPG Keys sections of the Containerfile, including any `rpm --import` line for the key, and including `epel` again brings both back. A file with another enabled section still included, a key another included repo still names, and a key the base image ships keep their existing handling. If you include `epel-release` while excluding `epel`, the Containerfile and the audit report now say that its repo definition is not carried, which is true. The scan tarball, and a refine export with no repo excluded, are unchanged. A `.repo` file you modified on the host is also captured as a config file, and still ships while that config entry is included.
- **An EL10 export that uses EPEL builds**: EPEL 10's `epel.repo` names its key as `RPM-GPG-KEY-EPEL-$releasever_major`, and the scan read that path literally, found nothing and skipped the key without a word. The export copied `epel.repo` but not its key, and the build failed at `dnf install` with `Curl error (37): Could not read a file:// file`. The scan now expands dnf variables in `gpgkey=` paths with the values dnf uses on that host: `$releasever` and its major and minor parts from the release package or the host's dnf variable files, `$basearch` from the host architecture, and any other variable those files define, in both the `$name` and `${name}` forms, with backslash escapes read the way the host's dnf reads them. The key is recorded and copied at the expanded path, and the Containerfile, the audit report's Carried by Export column and refine's repo view all treat it as the key `epel.repo` names, so `epel-release` installs from the copied definition. A key the scan still cannot collect, because a variable is not defined, its value is not a plain file name, the file cannot be read or does not hold a PGP public key, is now reported as a warning that names the repo file and says what to do, instead of surfacing first as a failed build. A `gpgkey = ...` line with spaces around `=`, and a key list continued on indented lines, are now read as dnf reads them.
- **The stock Red Hat release key is read as a key**: `/etc/pki/rpm-gpg/RPM-GPG-KEY-redhat-release` opens with a paragraph of text before its first `-----BEGIN PGP PUBLIC KEY BLOCK-----` line, and the scan accepted a key file only when that header came first. It recorded the Red Hat key on every RHEL host as not being a key and printed a stderr line for every `redhat.repo` section that names it. A key file is now accepted when any of its lines begins with the armored header. A file with no such line is still refused and its content replaced, and so is a file that also holds a PGP private or secret key block. Whether the key is then copied into the image is decided as for any other key the base image ships (see Changed).
- **A GPG key that several repo sections name is recorded once**: the scan recorded a key once for every section that names it, so a RHEL host's snapshot held one copy of the stock Red Hat key per `redhat.repo` section (209 on a RHEL 10.2 host, 500 on RHEL 9.8) and EPEL's key three times per `.repo` file. Each key path is now recorded once, with every `gpgkey=` path that named it. Rendering and refine still handle a snapshot with repeated entries for one key. A snapshot written by an earlier version has an older schema version, which the loader rejects.
- **The Containerfile no longer copies a repo directory the export did not write**: `COPY config/etc/yum.repos.d/` was emitted whenever the snapshot held an included custom repo file, even when every one had a path the export refuses and so never staged the directory, which failed the build. The copy and the `Custom Repositories (N)` count now follow the repo files the export actually wrote; each refused file keeps its `# FIXME`.
- **Language package paths with shell characters render again**: a pip, npm or gem project whose path held `$`, `;`, `&`, `|` or a backtick, such as `/opt/app$canary/venv` or `/srv/a&b/webapp`, was skipped with `# WARNING: path contains unsafe characters` since v0.9.0-beta.2, although every place the path is written in the Containerfile single-quotes it. Such a path now renders its install as it did in v0.9.0-beta.1. A path holding a single quote or a newline is still skipped with the warning.
- **The missing-`readelf` warning no longer points at a container image**: when `readelf` is not installed the scan skips its search for compiled programs under the scan roots, and the warning told you to install binutils "in the inspectah container image", which no longer exists because the scan runs directly on the host. The warning now says what the skip means: hand-installed (non-RPM) compiled programs under the scan roots were not detected. It no longer suggests installing anything.
- **A package dnf installs alongside one you kept now counts as pulled in**: the dependency list recorded for each leaf package followed only plain hard requirements. It skipped requirements on a file, so `git` did not list `perl-interpreter` (needed through `/usr/bin/perl`) and `httpd` did not list `mailcap` (through `/etc/mime.types`). It skipped weak dependencies, which dnf installs by default on rhel-bootc 9 and 10, so `httpd` did not list `mod_http2`. And it skipped conditional (rich) dependencies such as `(cockpit-ws-selinux if selinux-policy-targeted)`. Packages missing from that list read as not needed by anything you kept, so an excluded one lost its `systemctl enable` line, or was left out of a disabled repo's transaction, although dnf installs it. The list now follows file requirements, Recommends, Supplements and conditional dependencies, judged against what is installed on the host. A Supplements that needs several packages present together, such as `(shared-lib and desktop)`, counts only for a leaf that brings all of them, not for every leaf that brings one. A version in a conditional dependency is checked, so `(plugin if engine >= 2 else fallback)` counts `fallback` on a host with only `engine` 1, and a version floor such as `(foo >= 2 if foo)` does not count `foo` when nothing else installed provides `foo`. `with` and `without` match one package at a time, as rpm defines them. If the scan cannot read which package owns each file, the list comes from dnf instead, or is marked unavailable, rather than silently missing every file requirement. Suggests are still not followed, since dnf does not install them by default. A snapshot written by an earlier version keeps its old lists until the host is scanned again.
- **A leaf package no longer depends on packages it does not need**: the scan resolved the capabilities that added packages require in batches of 50 and credited every provider in a batch to every capability in it, so unrelated packages were recorded as dependencies of each other. On a RHEL 9.8 host, 25 of 26 leaf packages had the same 114-package dependency list, with `tree`, `htop` and `wget` each depending on `nginx-core`, `httpd-core` and `rsyslog`. That list decides which excluded packages still count as present because something you kept depends on them, so an excluded package could keep its `systemctl enable` line, or be named in a disabled repo's transaction, when nothing installs it. Each capability now maps to its own providers only, which changes the dependency lists in a new scan and therefore which packages count as dependencies. A snapshot written by an earlier version keeps its old lists until the host is scanned again.
- **A multi-value sysctl set to its configured value no longer reports as drift**: the kernel prints values such as `net.ipv4.ip_local_port_range` tab-separated while sysctl.d files write them space-separated, and the two were compared as raw strings, so `1024 65535` in a file against `1024<TAB>65535` at runtime read as a difference (measured on a RHEL 9.8 host). Values are now compared token by token, so the sysctl drift report lists only a real difference in value. The values stored in the snapshot are unchanged.
- **Unmanaged file exclusions no longer hide sibling paths**: `--exclude-path` entries and the language environment roots found elsewhere in the scan were matched as bare string prefixes in both unmanaged walks, so `--exclude-path /opt/app` also hid `/opt/app-data` and `/opt/app.conf`, and a language environment at `/usr/lib/node_modules/foo` hid a sibling `foo-cli`. Those files silently dropped out of the scan output, and the `/opt` ones out of the report and the image as well. An entry now covers the path itself and everything beneath it, and nothing else. A trailing slash on the entry is still accepted.
- **Unmanaged file provenance no longer leaks to sibling paths**: the writable mount and service workdir signals matched mount points and `WorkingDirectory=` values as bare string prefixes, so `/opt/application` was flagged for a service working in `/opt/app`, and `/srv/data-old` took the read-write flag of a `/srv/data` mount. On ostree hosts, the internal `/var` filter also dropped siblings such as `/var/lib/flatpak2`. Each now matches only the path and what lies beneath it.
- **A pre-loaded base image now works on a disconnected host**: the scan ran `podman pull` on the baseline image every time, and podman contacts the registry on every pull even when the image is already stored. A host with no registry access that had the base image from `podman load` therefore stopped at exit 3 before any inspector ran, which is the air-gap workflow the docs describe. The scan now checks local storage first and uses the stored image without pulling, printing `Using local image` in place of the `Pulled` line, and the line before extraction now reads `Preparing baseline image` instead of `Pulling`. A stored image is not refreshed, so pull it again or remove it with `podman rmi` to scan against a newer build. A `podman create`, `start` or `exec` failure after that is no longer reported as a pull failure: the error names the step, and for a stored image says nothing was pulled instead of pointing at the registry.
- **`--scan-home all` no longer scans the whole filesystem**: it selected every user with UID 1000 or higher, which on RHEL includes `nobody` (UID 65534, home `/`), so `/` became a scan root and every non-RPM walk ran over the entire host. `all` now selects UIDs 1000 through 59999, the range the users inspector already reports as regular users, and a home of `/` or an empty home is never added as a scan root, even for a user named explicitly. Paths found under a root of `/` (from `--scan-path /`) or under a home with a trailing slash no longer print as `//home/...`. Homes and `--scan-path` values are normalized first, so a home spelled `/.` or `//` is refused like `/`, a home or path with a `..` segment is refused, and a trailing slash or `.` segment in `--scan-path` is dropped.
- **Excluding a package no longer leaves its service in `systemctl enable`**: the unit stayed in the enable list with an advisory that no surface showed, so excluding `nginx` in refine produced a Containerfile that failed at `Failed to enable unit, unit nginx.service does not exist`, with no warning anywhere. A unit whose owning package is excluded is now left out of `systemctl enable`, `disable` and `mask`, and the Containerfile records it as `# Omitted: nginx.service (package 'nginx' was excluded)`, which the Omitted Services list in refine shows as well. This applies to an aggregate (fleet) export as well, where a package left out by the prevalence default counts as excluded. A package the baseline is known to ship keeps its unit, and so does a package that something you kept depends on, since dnf installs it anyway: that covers a dependency refine starts excluded and one you exclude yourself. The dependency is read from the scan's leaf data, which records the dependencies of leaf packages only; when the scan has no leaf data, or one leaf package depends on another, an excluded package's unit is still left out, and you enable it by hand if dnf pulls the package in.
- **A package from a repo disabled on the source host installs from that repo**: a package from a repo the host keeps at `enabled=0`, such as `openh264` from `epel-cisco-openh264`, was listed both in the main `dnf install` list and in the MANUAL block, and the build failed. When the export carries the repo's `.repo` file and the keys it names, the package now installs once with `--enablerepo=<repo id>`. Otherwise it stays in the repo-less block.
- **An npm project missing a manifest no longer breaks the build**: a project with a `package-lock.json` was marked high confidence whether or not its `package.json` was there or could be read, and high confidence renders an active `COPY` of both files followed by `npm ci`. A lockfile with no `package.json` beside it therefore produced a `COPY` of a file the export never wrote, and `podman build` stopped there; `npm ci` would have refused the single file in any case. A project is now high confidence only when both manifests were read, and the Containerfile checks that both are held whatever confidence the snapshot records, so a snapshot written by an earlier version renders safely too. Anything less renders a commented block for you to finish, and its manifests are no longer staged under `language-packages/npm/`, since no active `COPY` would carry them. That block no longer offers commented `COPY` lines for files the export does not carry: it names any manifest that was not captured and says to put both in the project directory before running `npm ci`.
- **Refine no longer pre-excludes a package whose disabled repo ships in the export**: refine starts every repo-less package excluded, so that a package of unknown origin needs a deliberate include. A package from a repo the host keeps disabled was caught by the same rule, even though its `.repo` file, with a source, is right there in the export and the scan tarball installs it from that repo with `--enablerepo`. Such a package now keeps its ordinary default in refine, so opening refine and exporting without changes installs it the same way the scan tarball does. `@commandline` packages, packages whose repo file is missing or excluded, and packages from repos that no longer exist still start excluded. The package still has no row of its own in the refine package list.
- **Warnings in `README.md` and `audit-report.md` print host text as written**: a warning naming a host value, such as a file, repo file or unit whose name held `*`, `[`, `<` or a newline, was written into the Warnings list as Markdown, so it could add emphasis, a link or HTML, or split the list item. Each message now renders as a code span. The HTML report already escaped them.
- **A repo defined in two files is judged by the copy dnf uses**: refine's repo status and the audit's "Carried by Export" now follow the `.repo` file dnf reads first, not the host's file order. A repo-enabling package that copy cannot serve, because it is disabled, has no source or names a key the export does not copy, gets the FIXME instead of a failing install. The FIXME names a file only when re-including it would serve the package.
- **Excluding a repo in refine no longer excludes its case variant**: dnf treats `site` and `SITE` as two repos, but excluding `site` also excluded the packages from `SITE` and left out its `.repo` file and GPG key. Each now follows its own toggle. The CodeReady Builder `--enablerepo` flags likewise keep each id's exact spelling, so two CRB repos that differ only by case are both enabled.
- **A repo-enabling package whose repo the export dropped accepts the upload its FIXME asks for**: when the repo that serves a package such as `epel-release` is not carried by the export, the Containerfile tells you to re-include the repo or upload the RPM, but refine refused the upload, because it checked the package against the scan rather than against your current choices. The upload is now accepted, the package installs from it, and the FIXME goes away. If you re-include the repo afterwards, the package installs from the repo again and the upload is left out of the export.
- **Repo-less RPMs install before the packages and services that need them**: the block that installs a cached or uploaded RPM with `dnf localinstall` was placed with the non-RPM software, after `systemctl enable` and after the main `dnf install` list. A unit owned by such a package was enabled before the package that ships it was installed, and a package that depends on it was installed before it, so either step could fail the build. Each such RPM is now copied into the image and installed from that file by the same `dnf install` that installs the packages from repos disabled on the source host, so dnf resolves the two together in either direction. That step runs after the repo-enabling packages and before `dnf group install`, the main `dnf install` list and every service action, and it carries the CodeReady Builder flags when those are carried. The MANUAL and FIXME notes for repo-less packages the export cannot install follow it under `Repo-less RPM packages`.
- **Removing an uploaded RPM says why it was refused**: when the snapshot records an uploaded RPM somewhere other than this session's upload directory, or the name there is not a regular file, refine refuses to delete it, and the response was a bare `500` reading `internal error`. It is now a `409` that names the file and the reason, for example `refusing to remove foo-1-1.noarch.rpm: the snapshot records it outside this session's upload directory`. The message names only the file name, never the upload directory or any other host path; the full detail, directory included, is printed to the refine server's standard error, with control characters escaped (a newline prints as `\n`), so a path or tarball name holding a newline or a terminal escape sequence cannot forge a second log line or drive the terminal. Every other server error is still a plain `internal error`.
- **The web UI's development server no longer has its changes refused**: the development server (`npm run dev`) forwarded requests to refine with the page's own origin, such as `http://localhost:5174`, which is not the origin refine serves, so refine refused every change made from that page. The development server now presents the refine origin in place of its own page's origin only; a request from any other origin is forwarded unchanged and still refused. The UI that `inspectah refine` serves itself is not affected.
- **Refine shows a failed user change on the user card**: when changing a user's Containerfile strategy, or choosing "No password" or "Keep existing password", failed, the card came back unchanged and the error went only to the browser console. The card now says which change failed and to try again, also when the failure lands while you are on another section, and clears the message when a retry succeeds. A failure is dropped after a reset to defaults, after an undo or redo that changes that user, and when the user leaves the list and comes back. Screen readers now announce this message and a failed new password when they appear.
- **Closing the RPM upload dialog no longer abandons the upload**: closing the dialog while an upload was running reset it without stopping the request, so you could start a second upload, and the first one's result could appear in the dialog opened for another package. The dialog now cannot be closed until the upload finishes, and a double click on Upload sends one upload.
- **Refine keeps a saved session it cannot load**: when the saved session beside a scan tarball could not be read, `inspectah refine` deleted it, printed `Discarded previous session.` without saying why, and started a fresh session. It now stops with an error that names the session file and why it could not be loaded, leaves the file as it was, and says that running again with `--fresh` discards it. `--fresh`, and the "Start fresh" answer when a saved session is offered for resuming, discard it as before.
- **An aggregate lists a unit once when its hosts disagree about its state**: a unit enabled on some hosts and disabled on others was in both the enabled and the disabled list of the aggregate snapshot. The unit inventory now has one entry for it, with the state most hosts have.
- **A masked unit is no longer also recorded as an empty full shadow**: a mask, a link to `/dev/null` or a zero-length file in `/etc/systemd/system/`, matched the full-shadow test, so the scan also recorded it as a drop-in with no content and the export copied it as an empty file. A mask is now one masked state, carried only as `systemctl mask`. A link that reaches `/dev/null` or a zero-length file through other links, `/etc/alternatives` for example, is a mask too, as systemd reads it: the scan called it an alias, dropped the mask with a warning, and the vendor unit came back in the image. A drop-in beside a mask is labelled a drop-in, not a full shadow that replaced the vendor unit.
- **A local unit's enable no longer runs before its unit file is copied**: the `systemctl enable` lines came before the configuration `COPY`, so enabling a unit whose file only the export supplies failed the build. They now come after it.
- **`dbus-broker.service` is no longer dropped**: the scan skipped every unit whose name starts with `dbus-`, to leave out D-Bus activation aliases. Only `dbus-org.` names are skipped now.
- **A unit file or drop-in that is not valid UTF-8 no longer marks the units inspection incomplete**: the scan reported the units section as degraded. Its `[Install]` cannot be read, so the unit gets the advisory for an `[Install]` section the scan cannot rely on (see Changed) and no `enable` or `disable`; a mask over such a file is still carried. A file under `/etc` is reported as content not captured on its Configuration Files row, and the unit's advisory becomes an `# Omitted:` line naming it.
- **A file the export cannot write fails the export**: a staged file whose path was already a directory, or whose directory could not be created, was skipped with a warning on stderr while the Containerfile still copied it. Any failed write is now an error naming the file. Two collected files with different content at one path, or a file and a directory at one path, are both withheld and named in a `# FIXME:`, a zero-length file at a unit path in `/etc/systemd/system/` is withheld since systemd reads it as a mask, and two spellings of one path are one file. The same file offered twice with the same content is written once. Where a configuration file is also a repo file, GPG key or firewall zone, its included Configuration Files entry supplies the exported content over the file's repository, key or firewall-zone record, and the repo file stays in the export; on a fleet aggregate, selecting a different variant of the file in refine does not yet change which variant is included. A unit file inspectah generates, a cron-converted timer or its service or the flatpak provisioning service, is never written over a collected unit of its name: every file of the generated unit is withheld, as the entry on generated units above says. The kernel arguments file inspectah generates is decided like a collected file: a different collected file at `/usr/lib/bootc/kargs.d/inspectah-migrated.toml`, or one under that path, withholds both, and the kernel arguments block is left out. A path longer than 4096 bytes, or with a component longer than 255 bytes, is refused and named in a `# FIXME:`, and `/api/view` names its rule, `TooLong` or `ComponentTooLong`. On a case-insensitive staging filesystem, the default on macOS, two included files whose paths differ only by case cannot both be written: the export fails with an error that names both paths, and you exclude one of them. Refine does not show this before the export.
- **What refers to a staged file follows the export's decision**: a unit file another section writes that the export withholds, the flatpak provisioning service, a cron-converted timer or its service, an `@reboot` service or a local timer, is neither copied nor enabled, where the build used to fail at a `COPY` or an enable naming a file the export did not write. A `/var` directory whose `/etc` tmpfiles.d fragment or unit file the export withholds is provisioned, and a unit file staged under another spelling of its path counts as carrying its directories. The GPG Keys heading and the firewall zone comment count only the files the export stages.
- **Excluding a unit's `[Install]` drop-in leaves its command out**: a unit made installable, or linked into another target, by a drop-in in `/etc/systemd/system/<unit>.d/` kept its `enable` when that drop-in was excluded in refine, and in the image `enable` read an `[Install]` the source host did not have. The scan now records each unit's `[Install]` drop-ins, and the export leaves the command out with an `# Omitted:` line when one of them is excluded, or when it would copy an `[Install]` drop-in for the unit that the scan did not record. An `/etc` drop-in with no `[Install]` section that hides a vendor drop-in of the same name counts too, since excluding it brings the vendor section back. A drop-in whose name starts with `.`, such as an editor's `.#override.conf`, never counts: systemd does not read it.
- **`.upholds` links are no longer copied as configuration files**: the configuration walk skipped links in `*.wants/` and `*.requires/` under `/etc/systemd/system/` but followed one in `*.upholds/`, so it recorded the linked unit's content at the link's path and the export copied a plain file where the link was. Those links are now skipped too, and reported as unit links (see Added).
- **The empty Systemd units section no longer says "No service state changes detected."**: the section covers sockets, timers, paths and mount units too, so it now reads "No unit differs from its preset, and no drop-in was found."
- **Section search works in the Systemd units section**: pressing `/` there opened a search that never appeared. It now filters the rows by what they show, including a link's relation, an undetermined install's reason and a mount unit's mount point.
- **A locked unit row names the reason instead of a slug**: the badge and the checkbox label of `dnf-makecache.service`, `dnf-makecache.timer` and `packagekit.service` read "Incompatible with image mode", where they printed `service-image-mode-incompatible`.
- **The Scheduled Tasks badge in the refine sidebar counts its toggles**: it read 0 on a host whose converted cron timers each have an include toggle, and the sidebar treated the section as cleared. It now counts every row with a toggle, less those shown with a reason instead.
- **The Containerfile panel footer in single-host refine covers every decision**: it said the preview reflects package and config decisions only. It now reads "Preview reflects every include and exclude decision you make in refine." The fleet view's footer is unchanged.
- **Redaction replaces only the secret, not its key**: `proxy_password = hunter2` becomes `proxy_password = REDACTED_PASSWORD_1`, so the stock `rhsm.conf` still parses. A redaction stays on its line and leaves an empty value such as `proxy_password =` alone. A quoted or XML value can still lose its closing quote or tag. A JDBC URL carrying a credential keeps only its scheme: `jdbc:mysql://REDACTED_JDBCPASSWORD_1`.
- **A database URL without a password no longer pairs with a later line**: a PostgreSQL, MongoDB, Redis or JDBC URL could match across line breaks, so `postgres://db/app` followed later by `contact: ops@example.com` redacted ` ops` as a password and rewrote that line. These patterns now match within one line.
- **`secrets-review.md` gives the line each secret is on**: the Line column was one too high for a secret whose match did not start its line, such as an indented `password = ...` or a `proxy_password = ...` line.
- **`secrets-review.md` names the tokens redaction writes**: it said secrets were replaced with `[REDACTED-*]` tokens, a form that appears nowhere in the export. It now gives the real form, `REDACTED_<KIND>_<N>` such as `REDACTED_PASSWORD_1`, and the markers used for URL credentials.
- **A malformed SELinux port label renders a FIXME instead of a command**: a port label with a type, protocol or port that `semanage port` does not take, such as port `70000`, rendered a `RUN semanage port` line the build could not run. It now gets a `# FIXME` line and no longer installs the SELinux policy utilities on its own.

### Security
- **The refine export keeps every file it extracts from the scan tarball inside the export directory**: the export copies included unmanaged files out of the source scan tarball, and both the file list and the tarball entries come from that tarball, so a crafted one could write anywhere the refine user can. Three routes reached outside the export directory: a path containing `..`, a symlink entry followed by a regular file at the same path (the file was written through the link), and a symlink entry at a directory followed by a file beneath it. The export now fails on an entry path with a `..`, root or `.` component, on a second entry at a path it already wrote, on any existing symlink or non-directory where it needs a directory, and on an existing file at the destination. An unmanaged hardlink entry, which used to become a symlink, now fails the export, as do device and FIFO entries. Unmanaged symlinks themselves are kept as they are, with their absolute targets, and the export never writes through one. The same path check now applies to fleet aggregate variant paths written under `aggregate/variants/`, where a `..` or a leading `//` also escaped the export directory: such a snapshot is refused as untrusted.
- **A line starting with `//` or `;` is no longer skipped by redaction in files where neither is comment syntax**: redaction leaves comment lines alone, and it treated a line as a comment if it began with `#`, `//` or `;`, in every file. In `fstab`, `sshd_config`, PAM files, audit rules and most `.conf` files only `#` starts a comment, so a line such as `//srv/share/password=hunter2` kept its secret in the export and produced no finding in `secrets-review.md`. `#` still marks a comment everywhere. `;` now does so only in `.ini`, `.cnf` and `.repo` files, in `smb.conf`, and in systemd's own files: units, quadlets, networkd files and `.nspawn` files under a `systemd` directory, `.conf` drop-ins in their `*.d/` directories, and daemon configuration such as `/etc/systemd/journald.conf`. `//` does so only in `named.conf`. Those are the files whose parsers read them as comments; a `.conf` elsewhere is not assumed to.
- **The scan tarball's cached repo-less RPMs pass the RPM filename allowlist before they are written**: `inspectah scan` copied each cached repo-less RPM into `repoless-packages/` under a filename built from the package's name, version, release and arch as the host's rpmdb reported them, with no check. A package name such as `../evil` put the copy outside that directory, and the scan usually runs as root. The Containerfile already refused such a name and left a FIXME in place of its `COPY`; the writer now runs the same allowlist, does not stage the file, and prints `Warning: cached RPM for <name.arch> not bundled` so the missing RPM is not a silent drop. Upload the RPM in refine to install that package.
- **npm global package names are quoted on the `RUN npm install -g` line**: the names and versions on that line come from each global package's `package.json` on the scanned host and were written into the `RUN` unquoted. A blacklist of `;`, `$`, a backtick, `|` and `&` was the only guard, so `>`, `<`, `(`, `)`, `*`, `{`, `}`, `#`, a space or a tab still reached the build: a package named `pm2>/etc/passwd` truncated a file inside the build container. Each token is now single-quoted, as in `RUN npm install -g -- 'pm2@5.3.0' 'typescript'`, on the active line and on the commented one alike, and a name or version holding a single quote or a newline is still skipped with a warning.
- **An npm global package name can no longer pass npm an option**: quoting keeps a name out of the shell, but a global package named `--prefix=/tmp/elsewhere` on the scanned host could still stand in for an npm option and move where the build installed every package on that line. The package list on the `RUN npm install -g` line, active or commented, now follows `--`, the conventional end-of-options marker, so no name can take an option's place.
- **Names taken from the snapshot can no longer write outside the export**: several export steps joined a name from the snapshot onto a directory in the export: a language-package manifest file name, a user name in `users/home/<name>/.ssh/authorized_keys`, and the names of timer and quadlet units. An absolute name replaced the directory and a name with `..` left it, so a crafted snapshot could overwrite a file such as another user's `authorized_keys` wherever the user running the scan or refine could write. Each of these names must now be a single plain file or directory name. One that is not is skipped and a warning is printed, and for a user's SSH keys the Containerfile carries a `# FIXME` in place of the `COPY`.
- **Refine enforces its archive size limits on the size it actually extracts, and reads only a real snapshot file**: when refine opens a scan tarball it refuses one that unpacks past 512 MiB or holds a file over 256 MiB, but it counted the size in each entry's basic tar header. A PAX record can override that size, and the extractor honours the override, so an entry that said 0 bytes could unpack to gigabytes. The limits now count the size the extractor uses. Separately, `inspection-snapshot.json` could be a symlink, which refine followed when it read the snapshot: one pointing at `/dev/zero` made the load allocate without end, and one pointing at a FIFO hung it. The snapshot must now be a regular file in the archive, and it is read with the same 256 MiB bound. Symlinks elsewhere in the tarball, such as those among the unmanaged files, are still accepted.
- **Refine bounds how much it decompresses from a scan tarball, extension records included**: the size limits above are checked on each file in the archive, but the tar reader loads a long-name record, a long-link record or a PAX record whole into memory before refine sees the file it belongs to. A small, highly compressible tarball holding one multi-gigabyte record could exhaust memory while refine opened it, before any limit applied. Refine now stops reading a scan tarball once it has decompressed about 590 MiB, the 512 MiB unpacked limit plus an allowance for tar headers, padding and long-path records, and refuses it. The refine export reads the source tarball again under the same bound.
- **Scheduled-task names can no longer add Containerfile instructions or enable a unit that was not exported**: timer and cron-converted unit names, and `at` job commands, went into the Scheduled Tasks comments as they appeared in the snapshot, so a name containing a newline ended the comment and the rest of it became an instruction the build ran. They are now escaped as comment text. Separately, a name the export refused to write as a unit file, such as one containing `/`, still got a `RUN systemctl enable` naming it; an absolute name enabled whatever unit file sat at that path in the base image. Such a unit now gets a `# FIXME` instead, and the export and the Containerfile decide which names are accepted with the same check.
- **The owning package in an `# Omitted:` comment can no longer add Containerfile instructions**: when a service is left out because its package is not in the image, the Containerfile records `# Omitted: <unit> (package '<name>' ...)`, and the package name was copied from the snapshot as is. An imported or edited snapshot whose package name held a newline ended the comment there, and the rest of the name became an instruction the build ran, under every omission reason: excluded, not in target image, and not carried. The finished comment line now has its newlines and carriage returns escaped, so the name prints as `x\nRUN ...` inside the comment. Refine's Omitted Services list shows the name as before.
- **Values from the snapshot can no longer end a comment line in any generated file**: the Containerfile, the `/var` tmpfiles.d fragment, the kickstart suggestion and the flatpak provisioning unit write values from the snapshot into `#` comments, and many of those values went in as they were: package names and architectures in the `# TODO:` manual follow-up lines, RPM group names, unmanaged file paths, pip, npm and gem project paths, static route files, `/etc/hosts` additions, proxy settings, the paths of excluded and flagged secrets, non-RPM binary paths and notes, and the hostname, connection names, routes and mounts in the kickstart suggestion. An imported or edited snapshot with a newline in one of them ended the comment, and the rest of the value became an instruction the build ran. Every comment line in those files now has its line breaks escaped, whichever they are: a newline prints as `\n`, a carriage return as `\r`, and a vertical tab, form feed, U+0085, U+2028 or U+2029 in `\u{2028}` form. Whatever the build makes of the ones other than the newline, a terminal or editor can treat them as a line break, so someone reviewing the file could be shown text it does not contain. Other control characters, such as the escape character that starts a terminal escape sequence, are escaped the same way; a tab is left as it is. A pip, npm or gem path, or an npm global package name, holding any of these line breaks is now skipped with `# WARNING: ... unsafe characters`, as one holding a newline already was, instead of reaching a quoted `COPY` or `RUN` line.
- **Every user field on the Containerfile's user lines is checked before it reaches a command**: the user name was checked, but supplementary groups, the login shell and the home directory went into `RUN useradd` as they appeared in the snapshot, and the password hash went into `chpasswd` without a check, so a home such as `/home/alice; id > /tmp/x #` or a hash containing a quote ran a second command in the build. User and group names must now be valid account names, which also refuses a name starting with `-`; the shell and home must be plain absolute paths and are quoted; and the hash must be a crypt(3) string. A user that fails any of these gets a `# FIXME` in place of its `useradd`, password and SSH key lines, a group gets one in place of its `groupadd`, and a hash that fails costs only that user's password. Password records are now passed to `chpasswd` with `printf`, one record per line, so more than one user's password is set correctly.
- **Values from the snapshot can no longer add a Containerfile instruction through a `COPY`, `FROM` or `dnf group install` line**: an unmanaged file path went into `COPY unmanaged/<path> <path>` bare, and the top-level directory of each config file into `COPY config/<dir>/ /<dir>/`. A path holding a newline reached the line unchecked, and the rest of the path would have started a new line of the Containerfile. A file name on Linux can hold a newline, so an unmanaged path does not need an edited snapshot to carry one. The target image reference went into `FROM` bare, and each package group name into double quotes on `dnf group install`, where `$(...)` and backquotes still run. Now a path on a `COPY` line may not hold a line break, control character, whitespace, `\`, `$`, or the wildcard characters `*`, `?` and `[`; a symlink recreated with `RUN ln -sf` may not hold a line break or control character in its path or target; an image reference is limited to registry, path, tag and digest characters; and a group name may not hold a line break, control character, quote, backslash, `$` or backquote, or start with `-`. Each refused value gets a `# FIXME` naming it instead of the line. A refused group's packages are installed one by one. A config file, repo file, GPG key, firewall zone or systemd drop-in whose path holds a line break, control character or `..` component is not written into the export, and the Containerfile names it in a `# FIXME`.
- **Values from the snapshot can no longer add a directive to the flatpak provisioning unit**: the unit that installs flatpak apps on first boot, which runs as root, wrote each remote name, remote URL, app id and branch into its `ExecStartPre=` and `ExecStart=` lines as they were, so a newline reached the line unchecked and would have started a new line of the unit, and a space, quote, backslash or `%` reached the command line unchecked. A remote name, app id and branch may now hold only letters, digits, `.`, `_` and `-`, and may not start with `-`. A URL may not hold whitespace, `%`, `$`, a quote, a backslash or `;`, and must start with a letter. A refused remote or app gets a `# FIXME` in the unit instead of its line.
- **Values from the snapshot can no longer add a kickstart directive or run a command at install time**: the kickstart suggestion wrote each `/etc/hosts` addition into `echo "<line>" >> /etc/hosts` inside `%post`, where `$(...)` and backquotes run during installation, and it wrote DHCP connection names into `network --device=` as they were. The users kickstart wrote user names, groups, home, shell, password hash and SSH keys into its `group`, `user` and `sshkey` lines as they were, so a newline reached the line unchecked and would have started a new line, and a space reached the directive line unchecked. Each `/etc/hosts` line is now written single-quoted, with `printf`, and one holding a line break gets a `# FIXME`. A device name must be a plain name. The users kickstart now checks users the same way the Containerfile does: a user whose name, groups, home or shell fails gets a `# FIXME` instead of its `user` and `sshkey` lines, a hash that fails costs only the password, and an SSH key holding a line break, quote, backslash, `$` or backquote gets a `# FIXME`.
- **Values from the snapshot can no longer add a key to the users blueprint, and no sysctl value reaches a line inspectah writes**: the blueprint TOML wrapped every string in quotes without escaping, so a quote or newline in a user's name, home, shell, groups, hash or key closed the string and added a key. Every string is now escaped as TOML requires. The blueprint also checks users the way the users kickstart does: a group, user or password hash the kickstart refuses gets the same `# FIXME` in the blueprint and is left out, so the two carry the same users. The SSH key is the one value carried on escaping alone. The synthesized sysctl drop-in wrote `<key> = <value>` lines unchecked, so a line break in a value would have started a new line of a file applied at boot. That drop-in is gone (see Removed): sysctl settings now reach the image only inside the host's own sysctl files, copied as they were, the same trust boundary as every other copied config file. Sysctl values are trusted as host configuration and applied as the source host had them, so a `kernel.core_pattern` that pipes core dumps to a program is carried as it is.
- **A name from the snapshot can no longer be read as an option or a comment on a `RUN` line**: package names, module names, streams and profiles, version-lock patterns, SELinux boolean names and values, and port labels were checked for shell metacharacters, but could still start with `-` or `#` (`--nogpgcheck`, `#foo`). Each such value is now refused and gets a `# FIXME` naming it: the package, module, version lock, boolean or port label is skipped. A package whose name was refused for any reason used to be dropped with no `# FIXME`; it now gets one. A unit the Containerfile enables, disables or masks is written after `--`, so a name that starts with `-`, such as the root slice `-.slice`, is an operand and never an option. The path of a GPG key, which `RUN rpm --import` takes as an operand, must be absolute: a relative one is refused with the GPG `# FIXME` and stays off both the `COPY` and the import line.
- **The refine server answers only requests addressed to a loopback name**: refine checked the `Origin` of changes but nothing on reads, so a web page you visited during a refine session could rename its own domain to 127.0.0.1 (DNS rebinding) and read every API response: the host inventory, configuration contents and, with `reveal=true`, any preserved password hashes. Refine now refuses, with 403, any request whose `Host` is not `127.0.0.1`, `localhost` or `[::1]`, on any port, so the UI and API still load through an SSH forward to a different local port. The check covers the page and its static files as well as the API. A request with no `Host`, or with more than one, is refused too; an HTTP/2 client may name the server in its `:authority` alone, which is checked the same way.
- **Credentials in podman output shown during a scan are redacted**: the baseline pull output and error messages redacted only the first bearer token, URL `user:password@` and `Authorization:` value, so a second one printed in clear, and never redacted a URL's query string, which can carry a download token or a signed URL's credentials, or the `token` fields of a registry's token response. Each occurrence is now replaced with `[REDACTED]`.
- **An AWS access key id after a comment line, or right after another key id, is redacted**: a key id on the line below a `#` comment kept its value in the export with no finding in `secrets-review.md`, and so did the second of two key ids one character apart, such as one per line.
- **Quoted credential values are redacted whole**: `"password": "x"` in JSON was not redacted at all, and `password: "two words"` kept everything after the first space. The whole quoted value is now replaced, so it loses its quotes and a JSON file no longer parses.

### Breaking
- **Snapshot schema 28**: a schema 27 snapshot no longer loads in `refine` or `aggregate`; re-scan the host. There is no migration. Schema 28 renames the `services` section to `units` and replaces its enabled, disabled and preset-matched name lists with one `inventory` that records each unit once, with its state and preset, masked units included. Each state change records its unit's kind, where its unit file is and which package owns it, and a new `mount_findings` list holds the administrator's mount, automount and swap units. A state change also records the units its `Also=` reaches and its `[Install]` drop-ins and, for an enabled template instance, the configuration it reads (`required_config`) and the data it keeps (`data_paths`), or why what it reads is unknown (`needs_unknown`), and the section records the hand-made links (`manual_links`), the units whose `[Install]` cannot be relied on (`undetermined_installs`) and the default target (`default_target`). A config entry a drop-in owns records `shadowed_by: "units"`. A scheduled timer no longer records `timer_content`, `service_content`, `disposition` or `locked`, and records the unit it starts (`trigger`) and the drop-ins that set it (`trigger_drop_ins`). A schema 27 snapshot still parses, but its unit section held services only, so every socket and timer state the host had is missing from it, and nothing in it says so. `MIN_SCHEMA` rises with `SCHEMA_VERSION`.
- **The refine API and saved sessions use `units`**: `/api/view` returns `unit_states` and `unit_dropins` instead of `service_states` and `service_dropins`, the section id is `units`, and an operation on a unit has kind `Unit`. A saved session containing the retired `Service` item kind does not load: `refine` stops with an error that names that kind, keeps the session file, and says that running again with `--fresh` discards it.
- **Snapshot schema 27**: a schema 26 snapshot no longer loads in `refine` or `aggregate`; re-scan the host. Schema 27 replaces the per-key sysctl overrides with the sysctl files and running values, read in systemd-sysctl's order. A schema 26 snapshot still parses, but it was collected before that order was followed, so an override in it may name a file the host never applied. `MIN_SCHEMA` rises with `SCHEMA_VERSION`.
- **Snapshot schema 26**: a schema 25 snapshot no longer loads in `refine` or `aggregate`; re-scan the host. Schema 26 adds the `content_not_captured` advisory. A schema 25 snapshot still parses, but a config file its scan could not read is in it as an included entry with empty content, and nothing in it tells that apart from a file that is really empty, so an export from it would copy the empty file over the real one. `MIN_SCHEMA` rises with `SCHEMA_VERSION`. Aggregates re-aggregate from re-scanned hosts.

## [0.9.0-beta.5] - 2026-11-05

### Changed
- **The refine export is assembled in one place** — `RefineSession::export_tarball` is removed and replaced by `RefineSession::export_plan`, which returns an `ExportPlan` the caller renders with `ExportPlan::render`. `POST /api/tarball` built its own copy of the same argument list, so the route and the session could disagree about what an export is without any test being able to see it: a change that made the route discard the operator's original include map passed the entire test suite. There is now one assembly and one list to get wrong. The download is byte-for-byte what it was; this removes a way for the two paths to drift, it does not change what either produces today. Library callers using `export_tarball` should call `session.export_plan(generation)?.render(&path)`.

### Fixed
- **The unmanaged `/usr` walk no longer reports the kernel and libgcc** — the rpmdb records some packages under the pre-usrmerge paths (`kernel-core` under `/lib/modules`, libgcc under `/lib64`), while the walk sees `/usr/lib/modules` and `/usr/lib64`. Ownership was a plain string match, so every file of those packages read as unmanaged: on a measured RHEL 10 host the kernel module tree alone was 108.9 MB of the 121.9 MB the section reported, and it advised copying the kernel into the image. A path owned under `/lib`, `/lib64`, `/bin` or `/sbin` now also counts as owned under `/usr`. A host without usrmerge is unaffected.
- **Unmanaged files under `/srv` are no longer copied into the image**: on fedora-bootc, centos-bootc and rhel-bootc `/srv` is a symlink to `var/srv`, so the Containerfile's `COPY` wrote that content into `/var/srv`, where it was unpacked once on first boot and never changed by a later image update. An included `/srv` finding now gets a comment block in the Containerfile and a note in the audit report instead, naming the paths and saying to carry them with the `/var` strategy: restore them into `/var/srv` after deployment, or give them their own mount. The files are still bundled under `unmanaged/srv/`. `/opt` and `/usr/local` findings are unaffected.
- **The unmanaged `/usr` walk honors the same exclusions as the unmanaged files walk** — it filtered only by RPM ownership, so `/usr/local`, which the unmanaged files walk already covers, was reported a second time. The same file got two `COPY` lines and two include toggles that did not know about each other, and a symlink there (an npm global such as `/usr/local/bin/ng`) was positioned to fail the second bundler with `File exists`. Paths given with `--exclude-path` and the language environments already counted elsewhere were also reported again under `/usr`. The `/usr` walk now skips every unmanaged files scan root under `/usr`, taken from the same list that walk uses, and applies both exclusions with the same prefix match.

## [0.9.0-beta.4] - 2026-11-04

### Changed
- **File context rules are replayed as real commands** — custom `semanage fcontext` rules were collected as raw table rows, and every one of them failed the renderer's shell safety check, so the generated build carried a FIXME in place of each of the first ten rules, nothing at all for any beyond that, and a commented-out `restorecon -Rv /` suggestion at the end. They are now collected as typed records and emitted as `semanage fcontext` commands that are valid against the target's policy. Order follows the source host's policy store when `file_contexts.local` and `file_contexts.subs` can be read, and the sorted output of `semanage fcontext -l -C` otherwise, with a note in the build saying which. Each label and unlabel rule removes its own key from the target's local store, then adds it, or modifies it when the target policy already defines the key; a rule whose path the target already maps as an equivalence is skipped at build time with a FIXME, because deleting its key would delete that equivalence. An equivalence rule instead reads the target's own mapping for its subject: added when absent, left alone when identical, and the build stops with an instruction when the target maps it elsewhere. There is no build-time `restorecon`, because a bootc target labels the deployed tree from the image's own policy. `/srv` is a symlink to `/var/srv` on the RHEL bootc base and the policy carries no alias for it, so a `/var/srv` equivalence is added once, ahead of the first `/srv` rule that needs it, to make the rules reach the real path.
- **A repo-enabling package installs from the repo that served it** — a `-release` package installed outside any repo rendered twice, once as an active install and once as a manual block, and the build could resolve neither reliably. Such a package is now recognised only when the host's enabled repos actually served it, the serving repo ids travel in the snapshot, and the export keeps the active install only while one of those repo definitions is still carried, enabled, and keyed, and every repo file and GPG key the package itself provides is still included. When no proof survives, the package is demoted to the upload path with an instruction naming the repo. A CodeReady Builder section enabled on the source host is carried as `--enablerepo` on the four `dnf` transactions that resolve against it: the repo-enabling bootstrap, the package list, the group install, and the module-stream enable.

Both now read the effective member set, the packages the operation would actually change, and an operation that would change nothing is refused with a message saying so. The repo switch reads the same counts and posts the direction it derives from them, in the same release, so no control it offers can post an op the server refuses. Its accessible name carries the repo id ahead of those counts, so two repos whose counts agree are still told apart by a screen reader navigating control to control.
- **`/etc` content is written from the Configuration Files decisions alone** — the export rewrote the kernel snippet directories after honouring those decisions, with no include check, so excluding a file under Configuration Files did not keep it out of the image, and RPM-owned unmodified `modprobe.d` files shipped in every build. There is now one source for `/etc` content. PAM files, audit rules, and custom tuned profiles become ordinary Configuration Files entries with their own include decision and their own rows in the reports.

Only a `d`, `D`, `v`, `q`, or `Q` entry at exactly that path, a unit `StateDirectory=`/`CacheDirectory=`/`LogsDirectory=`, or RPM ownership counts. The tmpfiles half of that is an exact-path lookup. The unit half is still a recursive text search with no line anchor and no boundary after the directory name, so a commented-out directive or a longer directory name under the same prefix satisfies it, and a vendor unit is matched even where an `/etc` override carrying no directive takes precedence over it. The export then checks whether that creator reaches the image and provisions the directory when it does not, or prints an instruction when it cannot tell. A unit named by two files, an `/etc` override and an RPM-owned vendor copy, is resolved by full path: excluding the override leaves the vendor unit as the creator rather than counting the directory as lost and adding a duplicate entry under whatever ownership the export guessed.
- **Uploaded RPMs keep their real filename and are proven before export** — an RPM whose filename did not match the host's exact version was matched, marked, and then silently left out of the build, so the build failed on a missing `COPY` source. Uploads are now staged under their own name through one allowlist, streamed to disk in bounded chunks rather than buffered whole, placed and recorded under one lock, and verified as a regular file inside the staging directory before the export copies them. A staged file that cannot be verified demotes its package with an instruction instead of failing the export.

"carried" was also the only one of the three still written in the code's own vocabulary, and it is the value that means "nothing to do here". Each outcome now leads with the word it is counted under: "backed: creator carried by this export", "unbacked: provisioned by this export", and "backing unconfirmed", which already matched.

Three things went with it: which of the two copies of that filename declared the directory, whether a second file declared it as well, and anything the search never looked at. The export then resolved the filename against RPM ownership, so a vendor package shipping a unit of that name counted as proof the directory gets created, whether or not that unit declares anything. Measured on a RHEL 9.8 host: an administrator's full shadow of `crond.service` adding `StateDirectory=crondstate`, excluded in the refine UI while `cronie` stays included, produced an export that called `/var/lib/crondstate` carried, wrote no tmpfiles entry for it and said nothing in the audit report. `cronie`'s own unit declares no directory at all, so the image would have had neither the creator nor the directory. The backing now records the full path of every file carrying the directive, and the export asks whether one of those files reaches the image: an included `/etc` unit or a carried vendor unit means carried, and an excluded shadow that is the only declarer means the export provisions the directory and names the creator it lost. The search also now covers `.mount` and `.swap` units beside `.service` and `.socket`, which is the full set `systemd.exec(5)` applies to, so a mount unit declaring a directory is no longer invisible.

### Security
- **RPM filenames are allowlisted before they reach a `COPY`, a `RUN`, or the filesystem** — an uploaded or cached RPM filename reaches four places in the generated build: a `COPY` source, a shell-form `RUN dnf localinstall`, the `rm` operand that follows it, and the commented copy of all three that a pre-excluded package carries. None of them was checked. The cached-RPM path built the filename from four snapshot fields and interpolated it straight into the `RUN`, so a scanned host reporting a package named `evil$(id)` produced a build that ran `id` as root, and the manual-resolution block put an unescaped package name in a comment, where a newline ended the comment and made the rest of the name an instruction. The upload handler had no allowlist either: it stripped the directory components off the name it was given and accepted whatever was left, so long as it ended in `.rpm`. There is now one ASCII allowlist, and one type that can only be built by passing it. The upload handler runs it and answers 400, the export runs it and demotes the package to a FIXME with a warning, the cached-RPM renderer and the source-tarball extraction run it and emit a FIXME instead of a `COPY`, and the upload-directory rescan on session resume runs it and leaves an unrecognised file unattached. A name the allowlist refuses is never sanitised into one it accepts. The export writes each uploaded package's file from the handle it verified rather than from a recorded path, and it is the only writer of that path.
- **Every host-sourced field of a `/var` provisioning line is allowlisted before it reaches a `RUN` or a tmpfiles.d entry** — the second instance of the same class, and the entry above does not cover it. A `/var` directory the export has to provision is named in a shell-form `RUN mkdir -p` when the scan captured no mode for it and in a tmpfiles.d `d` entry when it did, and nothing checked or quoted any operand of either. A snapshot carrying the path `/var/lib/app;id` produced a build that ran `id` as root. tmpfiles.d records are newline-separated and their fields whitespace-separated, so a newline in the path, the mode, the owner, the group, or the named creator each ended the record and started a second directive for systemd to apply at boot; the creator also reaches a Containerfile comment, where a newline ends the comment and promotes the rest to an instruction. The strongest of those needed no crafted tarball: the collector parsed `stat -c "%04a %u %g %U %G"` by splitting on the first four spaces, so the group name took the entire remainder of the output. That parse now requires exactly five whitespace-separated fields. The path and the three fields beside it are each proved by an ASCII allowlist carried in a type with no other constructor, and what a refusal costs differs by field: an account name degrades to the numeric id, which provisions the same ownership, while a refused path or mode has no stand-in that is still the host's and the artifact carries an instruction to create the directory by hand in place of the build step. The creator is escaped rather than refused, because it only labels a comment the operator is being asked to act on.

- **Rotate any credential a scanned host carried in a language-package manifest, a compose file or a quadlet unit, in every export taken with v0.8.7-beta.1 through v0.9.0-beta.3, and re-scan afterwards** — `inspectah scan` wrote every collected manifest into `inspection-snapshot.json` with no scrubbing of any kind. Upgrading does not close that: a credential already sitting in a tarball someone shared, in a fleet aggregate, or in a pushed image layer stays exposed, so rotation is the remedy here rather than a rebuild. All five formats were affected equally, `requirements.txt`, `package.json`, `package-lock.json`, `Gemfile` and `Gemfile.lock`, because the snapshot object never reached the scrubber at all: the redaction pass visited `.env` file content and git remote URLs and never `manifest_files`, and the renderer then serialized the snapshot whole. The sidecar under `language-packages/` was scrubbed correctly in the same export, two directories down from the copy that was not, and a project detected as `npm manifest`, a `package.json` with no lockfile beside it, gets no sidecar at all, so for those the unscrubbed snapshot was the only copy in the export. Three things kept it quiet. The scrub emitted no finding, so `secrets-review.md` said nothing about the credential and the README's `Secrets redacted` count did not include it, which on a host whose only secret was that credential meant the row was absent and the export looked clean. The snapshot was still eligible to be stamped `FullyRedacted`, because a manifest contributed nothing to weigh against it, and `FullyRedacted` is the one state the refine import path trusts to skip re-redaction, so a mislabelled snapshot stayed unscrubbed through a round trip. And the snapshot JSON is the artifact that goes in the tarball and that `aggregate` ingests across a fleet. The scrub now runs in the redaction pass, which owns the snapshot object that both export paths serialize, so neither path can be fixed without the other, and a manifest it scrubs emits a high-confidence finding, so the count the README prints and the state the import path trusts both describe what happened. The regression test asserts that no file anywhere under the export directory carries the fixture credential, rather than asserting about one named file. That qualification no longer needs making, because the line scanners it referred to are rewritten here too. **Eight span defects across six hand-rolled scrubbers are replaced by one primitive.** Every one was the same mistake: the scrubber found the right line and then took the wrong span, because it located the separator with a bare search from the start of the line instead of from the end of the key it had already matched. A compact `"publishConfig": { "registry": … }` gave up its credential because the first colon on the line belonged to a different member; `--index-url=URL` and `-i URL` are both valid requirements-file syntax and neither was recognised; a Gemfile `source` line with a quoted word in a trailing comment matched the comment's quotes; a `Gemfile.lock` line carrying two credentialed URLs kept the second; a compose `DATABASE_URL` whose value contained `?sslmode=require` split inside the query string. There is now one `value_span_after_key`, told which key the caller matched, searching forward from it, with four named syntaxes for the four forms its callers parse. **And a scrubber that cannot locate its value now says so.** That is the more important half. Previously a scrubber that failed to parse a line returned it unchanged and emitted nothing, so the snapshot stayed `FullyRedacted` over a credential nothing had examined and `secrets-review.md` was empty — measured on four separate inputs. A line routed to a scrubber by a key match whose value cannot then be located is recorded as an unresolved finding, which downgrades the snapshot to `PartiallyRedacted` and names the file and line for review. The finding deliberately carries no line text, because the premise is that the line may hold a credential nothing stripped and these findings are serialized into the export. A credential-free manifest comes back byte-identical, including its trailing newline, so the signal means what it says. **Three further fields had the same gap and are fixed with it.** A compose file's raw text and a `.timer` unit's text each reached `inspection-snapshot.json` the same way. A quadlet unit's text was worse than any of them: nothing scrubbed it anywhere, the quadlet collector raises no hint to hold the state down, and the renderer emits `COPY quadlet/ /etc/containers/systemd/`, so an `Environment=DB_PASSWORD=` line was copied into the built image at a path systemd reads at boot. Measured before and after inside a built image rather than only in the export. A `.timer`'s `Description=`, parsed into its own field, went the same way into the snapshot and the audit report. All four are now scrubbed where every other content field is, and two tests hold the class shut: adding a field to any content-bearing snapshot type fails to compile until it is classified, and a sweep plants a distinct secret in every one of them and asserts that exactly the fields declared exempt survive the export.

### Breaking
- **Snapshot schema 25** — removed fields, changed types, a new `shadowed_by` value, and a `/var` directory backing that records declaring paths rather than a unit filename make schema 22, 23 and 24 snapshots unloadable. `MIN_SCHEMA` rises with `SCHEMA_VERSION`. For 23 that is because the pass assigning a service-owned config file to a single owner runs at collect time, so loading an older snapshot would re-render from the state the pass exists to remove. For 24 it is more literal: the `unit` field is gone, so the payload does not deserialize, and the path it stood for is a collect-time observation no load-time migration could recover. Re-scan; aggregates re-aggregate from re-scanned hosts.

### Fixed
- **A redacted export's JSON manifests are still valid JSON** — the auth scrubber rebuilt each rewritten line with quotes that were already in the slices it was joining, so every value it touched came out as `""value""`. It ran on every `"resolved"` line of a `package-lock.json` and every `"registry"` line of a `package.json`, with or without credentials in them, so a redacted export's lockfile was unparseable throughout: 139 doubled quotes in the first one measured on a real host. `npm ci` reports that as a missing or too-old lockfile, which points nowhere near the export, and the build died at that step. Both export paths were affected once the manifest writer became shared, so a redacted CLI scan tarball corrupted its lockfile the same way the refine web download did. Unredacted scans were never affected. The regression test asserts the staged file parses as JSON; the suite that shipped this defect asserted only that the credential was gone and the host survived in the URL, both of which were true of the corrupt output.
- **A systemd drop-in has one include decision, not two** — a `*.service.d/*.conf` drop-in and an admin-written unit file in `/etc/systemd/system/` are recorded by two collectors, into `config.files` and into `services.drop_ins`, and the operator got a separate checkbox in each section. Only one of them governed whether the file reached the image. The export subtracts every service-owned path from the generic `/etc` tree without asking what the Configuration Files row said, while the Service Drop-ins writer skips excluded entries, so a file left checked under Configuration Files and unchecked under Service Drop-ins was written to neither tree and reached no image, with the checkbox still checked and no warning anywhere in the export. The reverse pair shipped a file the operator had unchecked. The two rows live in sidebar sections that are never on screen together and the search index did not cover the drop-in list, so nothing would prompt a comparison. The Configuration Files row for a service-owned path is now inventory, naming Service Drop-ins as its owner, and the server refuses a toggle on it from the web and CLI alike. The Service Drop-ins row is the one decision, and the export obeys it.
- **A shadowed Configuration Files row says where its control went** — making the row inventory stopped the two-checkbox contradiction, but in the web UI it left a row whose checkbox silently disappeared behind a bare "Inventory" badge, with nothing naming the control that replaced it. The badge is now the owner's name, "Controlled in Service Drop-ins" or "Merged into sysctl settings", beside the owner's current state and a link that jumps to the owning row with it focused. The join is the path string the shadow was computed from: `service_dropins[].path` for a service-owned file, `sysctls[].source` for one whose keys were absorbed. The Services section grew a group for drop-ins whose unit has no state change of its own, because a unit sitting at its preset state never reaches `state_changes` and its drop-in therefore rendered nowhere at all, which is the common case rather than an edge one. Global search now indexes the drop-in list by path and unit, so searching the path of a shadowed file reaches the row that decides it.
- **A service drop-in can be switched back on** — the Service Drop-ins toggle only moved one way. Including a drop-in was allowed only when its parent unit appeared in the services section as an included state change, but that section records a unit only when its enable state diverges from its preset; a unit sitting at its preset state is listed separately and has no entry there at all. For that case, which is the ordinary one, the include was refused permanently while the exclude was unguarded, so an operator who unchecked a drop-in lost the file for the rest of the session with no way back short of discarding the session. The Configuration Files row over the same path became inventory in this release, which left this the only control over the file. The refusal now tests for an actual exclusion of the parent rather than for the absence of a decision about it. Excluding a parent service still cascades onto its drop-ins and still blocks re-including one of them on its own, because that would undo the operator's parent decision for a single file. Measured on a RHEL 9.8 host and in the built image: a drop-in whose parent carries no `systemctl enable` line is correct output, not a hazard, because the image's own preset enables the unit exactly as the source host had it.
- **An admin-written unit file in `/etc/systemd/system` reaches the configuration inventory** — the walk's alias-symlink exclusion never asked whether the path was a symlink. It stripped `/etc/systemd/system/` and dropped anything with no `/` left, which is a nesting-depth test: drop-ins under `*.service.d/` survived it and whole unit files did not. An operator's full shadow of a vendor unit, and any wholly new unit written straight into that directory, were discarded from `config.files` for having a short path, while the alias symlinks the rule was named for were excluded only by coincidence. The check now tests the file type. A symlink there is systemd's own state, an alias from `systemctl enable` or a mask link to `/dev/null`, and both are already recorded by the services inspector; a regular file is admin-written content and is kept. Measured on a RHEL 9.8 host carrying synthetic drift: five unit files entered the inventory that a scan of the same host had been dropping, the two masked units stayed out, and the exported tree did not change, because a path the services section already carries is still written from there alone.

- **A failed RPM upload no longer reports success** — the refine web UI branched on the response status alone and never read the server's `{"error": "…"}` body, and the upload modal caught the resulting error and discarded it. Every refusal left the green "`foo.rpm` matches nginx" checkmark on screen with the Upload button live again, so an operator whose upload was rejected for its filename, its size, or a staging conflict saw nothing at all go wrong. Both upload routes now surface the server's reason: the modal replaces the checkmark with the refusal text and offers no retry, and the status code rides along in the message because two of the reasons ("internal error", and axum's "failed to read stream" for a body over the 500 MiB route limit) say nothing on their own. The DELETE route had the same defect and the same fix, so removing a package whose RPM came from the host's dnf cache now reports why instead of logging "Conflict".
- **Reference sections no longer lag behind the session's own decisions** — two surfaces answered from a projection of the session's original snapshot, built once and cached for the server's lifetime. Once a decision was made, the cached surfaces kept reporting the original include state: a Configuration Files exclusion dropped the file from the export while its Kernel and Boot mirror kept reporting it included, and the Storage view reported a /var directory as carried while the export wrote a provisioning line for it. A resumed session's first read reported an exclusion it had just replayed as still included, since the cache read the pristine snapshot rather than the replayed state. Both caches are gone: reference sections now project from the live session on each request.
- **Both export paths now carry every directory their own Containerfile copies** — the third and fourth instances of the same class as the tmpfiles entry below, and they are mirror images: each export path emitted a `COPY` the other path satisfied. The refine web download deleted `quadlet/` from the archive after the config tree had written it, on the stated grounds that the Containerfile referenced quadlets through `config/` paths, which it never did; so every download taken from a host running quadlets failed `podman build` at `COPY quadlet/ /etc/containers/systemd/`, in all four combinations of the operator's config and container toggles, with no export warning. In the other direction, the pip/npm/gem manifest writer lived in the refine crate alone, so the CLI scan tarball emitted `COPY language-packages/...` for a directory it never wrote and failed there instead. The manifest writer now sits beside the renderer that emits those `COPY` lines and both paths call it, and `quadlet/` is part of the refine export. A test over both paths asserts the general invariant: every `COPY` source the renderer emits exists in the export tree rendered alongside it.
- **The refine web download's Containerfile no longer references a tmpfiles fragment the archive doesn't contain** — the tarball downloaded from the refine UI emitted `COPY config/usr/lib/tmpfiles.d/inspectah-var.conf` in its Containerfile without writing that file into the archive, so `podman build` failed on a missing COPY source with nothing said beforehand. The CLI's own render path wrote the member correctly; only the web download's export path skipped it. The mismatch predates this phase, but it previously needed a scan verdict of an unbacked /var directory, which no decision in the UI could produce. This phase made it reachable by decision: excluding a tmpfiles.d fragment under Configuration Files now provisions the directory and emits the COPY line, so an ordinary UI action could produce a download that fails to build.
- **An unreadable directory under `/etc` marks the scan partial**: the main `/etc` walk recorded a permission failure on a subdirectory and then dropped it unless the whole walk came back empty, so on any real host the config inspector reported complete while that subtree's files were missing from the export. The failure now degrades the config inspector, and the scan reports partial. A host with any unreadable `/etc` subdirectory, for example `/etc/sssd`, now gets a partial scan where it used to get a complete one. This change shipped in 0.9.0-beta.4; the entry was added after that release.

## [0.9.0-beta.3] - 2026-08-16

### Fixed
- **RPM-owned paths containing a space were treated as unmanaged** — the owned-path set was built from the first whitespace-delimited field of each `rpm --query --all --dump` line. `rpm` quotes nothing and puts the path first, so an owned path containing a space was cut at that space and never entered the set. ## [0.9.0-beta.2] - 2026-08-16

### Fixed
- **Config advisories no longer count as files you excluded** — section stats bucketed every finding by its include flag, so an advisory landed in the excluded count. The refine stats bar read "0 included / 1 excluded" beside the advisory row it was describing, and the TUI's System Configuration badge, which reports advisories as whatever the decisions leave over, read "0 adv" for a group holding two of them. Section stats now carry a third `advisory` bucket, and the three partition the section. The refine web stats bar and the TUI status bar each render that bucket as a third counter on the sections that have one, and stay two-counter bars on the hosts that have none — before, a three-item config section holding two advisories read "1 incl / 0 excl" on the TUI bar, leaving two of its three items unaccounted for. The export dialog no longer counts advisories among the files you excluded; it reports them separately, noting that they are listed in the audit report while their files are not copied into the image.
- **A space in a venv directory name broke the generated build** — the venv directory name is interpolated into `/tmp/<name>-requirements.txt`, a separate token from the venv path and outside the quotes that path gets. A legal path like `/opt/app/my venv` rendered a three-argument `COPY` and handed `pip install -r` a stray token, so the build failed. All three interpolation sites now quote the name. This is a pre-existing issue predating 0.9.0-beta.1.
- **Comment-only values could emit live Containerfile instructions** — the npm global prefix and the pip package list are interpolated into comment lines, and neither was filtered. A newline in a prefix or in a package name closed the comment, and the rest of the value became an active `RUN` instruction in the generated Containerfile. pip package names come from `.dist-info` directory names, which a service account owning a venv under `/opt` can write. Both values are now escaped for their comment context. This is a pre-existing issue predating 0.9.0-beta.1, not a beta.2 regression.
- **Config advisories now appear in the reports** — modernization findings (sysvinit scripts and the rest of the pattern catalog) and cross-tree symlink findings are carried on the config entry's disposition, which every include-filtered table treats as excluded. They reached no report at all. Both the HTML and markdown audit reports now list them as advisories with their rationale, and the System Configuration group badge counts them.
- **Config advisories now appear in the TUI** — the same modernization and cross-tree symlink findings rendered in the TUI's Configuration Files section as excluded, toggleable files. They now render as advisory rows with the `ℹ` marker, their advisory type, and their rationale in the detail view, off the same collector the reports use.
- **Doubled leading slashes in language environment paths** — the npm global and system gem collectors stripped only the first leading slash, so a prefix reported as `//usr/lib/node_modules` was stored one way and rendered another. Every collector now strips all leading slashes, and the Containerfile renderer restores exactly one.
- **Shell metacharacter rejection widened** — the renderer safety guard for language-package paths and package names rejected only single quotes and newlines. It now also rejects `;`, `$`, backtick, `|`, and `&`, which matters most for npm global package names, since those interpolate into `RUN npm install -g` unquoted.
- **Orphan full-shadow services labelled as advisories in the HTML report** — a preset-matched service whose unit file is fully shadowed in `/etc/systemd/system/` has no state change to act on, but rendered as an ordinary included row in the service table and was left out of the group advisory badge. It now renders in the advisory list with its rationale and counts toward the badge, matching the audit report.
- **Advisory toggles are now refused, not silently ignored** — `SetInclude` on an advisory config finding (cross-tree symlink, modernization) returned success while discarding the change. It now fails with a clear "advisory item is not toggleable" error, matching the existing inventory behaviour.
- **Advisory and inventory findings no longer render as toggleable in the refine web UI** — the frontend read a finding's include flag as `disposition?.include ?? true`, and neither an advisory nor an inventory finding carries that key. Every one of them rendered as an item the user had chosen to bake into the image, with a live checkbox whose toggle the server discarded. The web contract now models all three dispositions, advisories render with their type and rationale and no toggle, and inventory findings render as inventory.
- **Language package pins are reachable from the keyboard** — a package row inside an expanded npm global environment was focusable and arrow-navigable, but Enter and Space did nothing there: the pin was reachable only by tabbing into the checkbox inside the row. Enter and Space now toggle the pin from the row, and the change is announced the same way a mouse click is.
- **Config advisories now appear in the refine web UI** — the same modernization and cross-tree symlink findings the reports and the TUI gained rendered here as excluded, toggleable config files, and a host whose only config finding was an advisory got an "all configuration files excluded" empty state that hid it entirely. They now render as advisory rows with their type and rationale, off the same collector the reports use, and a replayed pre-beta.2 toggle can no longer downgrade one to an included file.
- **A resumed stale toggle can no longer bake an advisory file into the image** — `resume_from` replays an autosaved timeline without re-validating each op, and the projection applied a `SetInclude` to a config entry unconditionally. A session saved before advisory toggles were refused could therefore replay one, rewriting a modernization or cross-tree symlink finding as actionable-included in the projection the export renders from — so the flagged file was copied into the image. The projection now preserves advisory and inventory findings, matching the merge layer.
- **Refused toggles return 422 instead of 500** — the refine web API answered a `SetInclude` on an advisory or inventory finding with a bare "internal error" at HTTP 500, which reads as a tool crash and hides the reason. Both refusals now return 422 with a message naming the item and why it cannot be toggled.
- **Advisory findings survive refine normalization** — opening a snapshot in refine overwrote advisory config dispositions with tier-based include defaults, erasing the rationale and letting the export copy a flagged file into the image. Advisory and inventory findings now pass through normalization unchanged.
- **Disposition defaults on snapshot re-render** — network connections, firewall zones, firewall direct rules, and the tuned profile selection no longer deserialize as "actionable, included" when their `disposition` key is absent from a snapshot. Network findings default to inventory and the tuned selection defaults to excluded, so `--from-snapshot` re-renders no longer bake inventory-only items into the Containerfile.

- **Deduplication uses ecosystem+path** — language environment dedup key includes ecosystem, preventing same-path npm+gem projects from collapsing. System pip now collects all packages into a single environment entry.

### Fixed
- **RPM upload matching** — uploaded RPMs now match repo-less packages by name and architecture instead of requiring exact NEVRA filenames. Supports non-standard filenames from vendor downloads, COPR, and manual builds. Upload endpoint now returns match status (`matched`/`unmatched`) with canonical `name.arch`.
- **RPM repo-less false positives** — repo-less detection now uses case-insensitive substring matching between install-time short names (`AppStream`, `baseos`) and full repo IDs (`rhel-9-for-aarch64-appstream-rpms`). Previously ~50% of packages were falsely flagged on real RHEL systems.
- **Python venv detection for "venv" directories** — removed `venv` from PRUNE_DIRS so the venv walker can discover environments at the most common path (`/opt/myapp/venv/`).
- **npm detection for projects without lockfile** — added package.json manifest fallback scan for npm projects without `package-lock.json`. Detected with method `npm manifest` and confidence `low`.
- **Ruby gem detection for system-installed gems** — added system gem detection via `gem list --local` with RPM ownership filtering. Detected with method `gem system` and confidence `medium`/`low`.
- **Duplicate repo display** — package tables now use the same repo identifier as the config tree. Source repo short names are normalized to full repo IDs using `.repo` file section headers.
- **Pip venv paths normalized** — venv renderer now produces absolute paths (`/opt/myapp/venv`) instead of relative (`opt/myapp/venv`).
- **Refine exclusion honored** — high-confidence language environments with `include: false` no longer emit active `COPY`/`RUN` lines.
- **Export contract test method strings** — test fixtures updated to use canonical method constants.

- **Aggregate sidebar simplified** — removed "N/M confirmed" ack progress labels from sidebar nav items. Item count badges remain.

- **Dark mode prevalence badge contrast** — prevalence badges now have proper dark-mode color overrides instead of hardcoded light-mode colors.
- **Keyboard navigation in aggregate mode** — number keys (1-9) now jump to the correct aggregate sections. Previously they sent single-host section IDs, causing partial navigation failures.
- **Aggregate default selections** — packages and config files in aggregate mode now correctly default to excluded when not present on 100% of hosts. Previously all items defaulted to selected regardless of prevalence, requiring manual deselection of partial-prevalence items.
- **False "unredact hashes" offer** — User Artifact Preview no longer shows the redact/reveal banner when the displayed content has no redacted material. ContainerfilePanel "Reveal hashes" button also hidden when the Containerfile has no crypt(3) hashes.

- **RHEL repo classification** — RHEL-style long repo IDs (e.g. `rhel-9-for-x86_64-baseos-rpms`) are now correctly classified as distro repos. Previously, only short CentOS-style IDs (`baseos`, `appstream`) were recognized, causing RHEL base repos to appear as toggleable third-party repos instead of always-on.
- **Ungrouped packages disappearing** — ungrouping a DNF package group now correctly surfaces individual members in the package list and Containerfile. Previously, non-leaf group members were filtered out by the leaf dependency filter after ungrouping. Removed the empty `# Ungrouped from "..."` Containerfile comment.
- **Inspectah COPR repo in config files** — inspectah's own COPR repo definition is now auto-excluded from config files and repo file output. The migration tool should never carry its own repo into the target image.
- **Group toggle removed** — removed the non-functional group-level toggle switch. Groups are managed via the ungroup button (dissolves into individual packages) or per-member actions.

## [0.8.6-beta.4] - 2026-06-22

- **Subscription cert expiry display** — scan output now shows entitlement certificate expiration date when `--preserve subscription` is used. Warns at <7 days remaining, errors if already expired. Also included in the generated README.

- **Container section quadlet content** — quadlet unit file content now viewable inline via expand/collapse in container section.
- **Sidebar subsection counts** — sidebar section counts correctly sum subsection items for subsection-only sections.
- **Accessibility improvements** — ContextList subsections use semantic headings and ARIA region landmarks.
- **Pull failure classification** — five error categories (registry unreachable, auth required, image not found, TLS/cert error, unknown) with tailored remediation guidance including disconnected-environment workarounds.
- Build metadata in version output — `inspectah version` and `--version` now show commit hash and build date
- Compile-time build script (`build.rs`) captures git revision and date

### Changed
- **CLI command rename** — `fleet` subcommand renamed to `aggregate` — all CLI commands, types, modules, and documentation updated
- **Mandatory baseline** — `--no-baseline` flag removed; baseline extraction is now required. Scans that cannot pull the target image exit with code 3 with remediation guidance. Use `--base-image` to override auto-resolution.
- **CLI flag rename** — `--baseline` flag renamed to `--target-image` (old flag still accepted as alias for compatibility).
- **Exit codes** — pull failures now exit with code 3 (previously the scan would continue with degraded output).
- **Scan progress output** redesigned as append-only streaming receipt.
- **Progress modes** simplified from three (rich/plain/flat) to two (pretty/flat).
- **Sub-step detail** moved behind `--verbose` flag.
- **Verbose mode** now works with both pretty and flat modes; flat mode respects `--verbose` (previously always showed sub-steps).
- **Tuned profiles** auto-enabled by default (previously required manual inclusion).
- **Schema version** bumped to 19. Tarballs from older schema versions are no longer loadable.

### Fixed
- **RPM performance** — massive speedup through batching: `dnf group info`, `rpm -qR`, and `--whatprovides` calls now batched into single invocations. Dramatically reduces scan time on hosts with many packages/groups.
- **Platform plumbing packages** hidden from refine view (installer-default packages no longer clutter migration scope).
- **User refinement operations** preserved after anaconda reclassification.
- **Config content truncation** removed (previously capped at 500 characters).
- **InstalledGroup members** filtered to installed-only packages (previously included uninstalled metadata).
- **Triage count badge** removed from UI (was noisy, not useful).
- **Subuid badge** removed from user cards.

### Removed
- **`--no-baseline` flag** — baseline is now mandatory.
- **`--progress rich` and `--progress plain` modes** (use `--progress pretty`).

### Known Issues
- RHEL-subscribed builds (`--preserve-subscription`) do not work when inspectah runs on non-RHEL hosts. The subscription material is host-specific and cannot be transferred across distributions.
